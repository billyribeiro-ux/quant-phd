Modern quantitative code bases must reconcile flexibility with zero runtime overhead. Polymorphism achieved via object-oriented virtual function tables incurs pointer indirection and inhibits compiler inlining. C++ templates provide compile-time parametric polymorphism, generating specialized machine instructions for each numeric type. C++20 concepts formalize type requirements, converting cryptic template errors into precise, readable compile-time diagnostics.

1Compile-Time Polymorphism versus Dynamic Virtual Tables

In traditional object-oriented programming, dynamic polymorphism routes member function calls through a Virtual Method Table (vtable) populated at runtime. Each polymorphic object stores a hidden virtual pointer (vptr). Calling a virtual method requires two pointer dereferences (fetching the vtable address, then indexing the function slot), preventing compiler inlining across the call boundary.

Definition 4.1 (C++ Templates and Concepts)

C++ templates and concepts form a compile-time meta-programming system. A template is a parameterized blueprint from which the compiler instantiates concrete functions or classes upon encountering specific type arguments. A concept is a named, compile-time predicate that constrains template type arguments, enforcing that a type provides required member types, operations, and expressions.

Proposition 4.2 (Inlining and Zero-Cost Dispatch)

Assumption 1: Function template \(f\langle T\rangle\) is invoked with concrete type \(T_0\).
Assumption 2: The definition of \(f\) is available in the current translation unit.
Statement: The compiler evaluates the call site with direct static dispatch, eliminating vtable indirection and permitting full cross-function inlining.

Proof

Under template instantiation, the compiler substitutes concrete type \(T_0\) into the abstract syntax tree of \(f\), synthesizing a non-polymorphic specialization \(f_{T_0}\). Because the target address is resolved statically during compilation rather than looked up via a runtime pointer, the invocation emitted is a direct call or inlined machine code. Inlining eliminates call instructions, stack frame creation, and register preservation, yielding zero runtime abstraction penalty. \(\blacksquare\)

2Type Traits, SFINAE, and C++20 Concepts

Prior to C++20, constraining templates relied on SFINAE (Substitution Failure Is Not An Error) and type traits from <type_traits> using std::enable_if_t. If substituting a type produced an invalid expression in the function declaration, the compiler discarded the overload from the candidate set rather than emitting an error. However, SFINAE resulted in notoriously verbose code and deeply nested compiler diagnostics.

Definition 4.3 (C++20 Concepts and Requires Clauses)

A C++20 concept is declared via template<typename T> concept Name = constraint_expression;. Constraints can combine boolean type traits (such as std::is_arithmetic_v<T>) or specify syntactic requirements via requires(T a, T b) { ... }. A function template applies constraints via the requires clause or inline concept shorthand (e.g. void price(std::floating_point auto s0)).

Proposition 4.4 (Concept Constraint Monotonicity and Subsumption)

Assumption 1: Concept \(C_1\) requires expression set \(E_1\) and concept \(C_2\) requires expression set \(E_2\) with \(E_1 \subset E_2\).
Statement: Concept \(C_2\) subsumes concept \(C_1\). When overload resolution evaluates candidate functions \(f(C_1)\) and \(f(C_2)\) for a type satisfying \(C_2\), the compiler deterministically selects the more constrained candidate \(f(C_2)\) without ambiguity.

Proof

The C++20 standard defines partial ordering of constraints via atomic constraint normalization. If every atomic constraint in the normal form of \(C_1\) is implied by the normal form of \(C_2\), but \(C_2\) contains additional atomic constraints, \(C_2\) is strictly more constrained than \(C_1\). Overload resolution rules specify that between two viable candidates, the more constrained candidate is selected as a better match, resolving static dispatch without ambiguity. \(\blacksquare\)

Lab 1 · Template instantiation and concept constraint evaluation

Simulating template instantiation with concept constraints verifies that arithmetic types compile and execute successfully, whereas invalid types (such as strings or non-callable functors) fail at constraint evaluation with explicit diagnostics.

"""CS5 Lab L04: Template instantiation, C++20 concept constraints, and compile-time dispatch.

Standard library only. Simulates compile-time type constraint checking, concept satisfaction,
SFINAE substitution failure, and static dispatch for generic pricing kernels.
"""

from __future__ import annotations

from collections.abc import Callable
from typing import Any


class ConceptViolationError(TypeError):
    """Represents a C++20 concept constraint dissatisfaction compiler error."""

    pass


def concept_floating_point(type_obj: type) -> bool:
    """Models std::floating_point<T> concept."""
    return issubclass(type_obj, float)


def concept_arithmetic(type_obj: type) -> bool:
    """Models std::is_arithmetic_v<T> concept."""
    return issubclass(type_obj, (int, float)) and not issubclass(type_obj, bool)


def concept_payoff_functor(fn: Any, arg_type: type) -> bool:
    """Models a C++20 Payoff<F, T> concept: requires F to be invocable with T returning T."""
    if not callable(fn):
        return False
    try:
        sample_input = arg_type(100.0)
        output = fn(sample_input)
        return isinstance(output, (int, float))
    except Exception:
        return False


class GenericPricerKernel:
    """Models a template class Pricer<T> with C++20 requires clauses."""

    @classmethod
    def instantiate(cls, value_type: type, payoff_fn: Callable[[Any], Any]) -> GenericPricerKernel:
        # Constraint 1: requires std::is_arithmetic_v<T>
        if not concept_arithmetic(value_type):
            raise ConceptViolationError(
                f"Compile error: type '{value_type.__name__}' does not satisfy concept 'std::is_arithmetic_v<T>'"
            )
        # Constraint 2: requires PayoffFunctor<F, T>
        if not concept_payoff_functor(payoff_fn, value_type):
            raise ConceptViolationError(
                f"Compile error: callable does not satisfy concept 'PayoffFunctor<F, {value_type.__name__}>'"
            )
        return cls(value_type, payoff_fn)

    def __init__(self, value_type: type, payoff_fn: Callable[[Any], Any]) -> None:
        self.value_type = value_type
        self.payoff_fn = payoff_fn

    def execute_batch(self, simulated_terminal_prices: list[Any]) -> list[Any]:
        results = []
        for st in simulated_terminal_prices:
            typed_st = self.value_type(st)
            results.append(self.payoff_fn(typed_st))
        return results


def run_template_concept_experiments() -> None:
    print("CS5 L04: C++ Template Instantiation and Concept Constraint Evaluation")

    def call_payoff(s: float) -> float:
        return max(s - 100.0, 0.0)

    # Valid instantiation 1: double (float)
    kernel_double = GenericPricerKernel.instantiate(float, call_payoff)
    out_double = kernel_double.execute_batch([90.0, 105.5, 120.0])
    print(f"Instantiation <double, CallPayoff>: satisfied, evaluated {len(out_double)} points -> {out_double}")

    # Valid instantiation 2: int64 (int)
    kernel_int = GenericPricerKernel.instantiate(int, lambda s: max(s - 100, 0))
    out_int = kernel_int.execute_batch([90, 105, 120])
    print(f"Instantiation <int64_t, CallPayoff>: satisfied, evaluated {len(out_int)} points -> {out_int}")

    # Invalid instantiation 1: string (rejected by arithmetic concept)
    try:
        GenericPricerKernel.instantiate(str, call_payoff)
        print("Template: Unexpected compilation success on str")
    except ConceptViolationError as err:
        print(f"Concept constraint rejection (non-arithmetic): {err}")

    # Invalid instantiation 2: non-callable payoff functor
    try:
        GenericPricerKernel.instantiate(float, "not_a_functor")  # type: ignore[arg-type]
        print("Template: Unexpected compilation success on non-callable")
    except ConceptViolationError as err:
        print(f"Concept constraint rejection (invalid functor): {err}")


def main() -> None:
    run_template_concept_experiments()


main()

4Where the Canon Breaks

Template instantiation generates a distinct copy of machine code for every unique combination of template arguments. In financial libraries supporting hundreds of asset classes, volatility surfaces, and numerical types, unchecked template instantiation causes binary code bloat. Bloated binaries degrade instruction cache (I-cache) hit rates, evicting critical pricing loops from L1 instruction caches and increasing latency. Mitigating code bloat requires explicit template instantiation (extern template) and factoring type-independent logic into non-template base classes.

5Misconceptions

  1. Templates incur runtime overhead compared to non-template functions.

    Templates incur zero runtime overhead. Template instantiation happens entirely at compile time, emitting optimized, direct machine code tailored to the exact type.

  2. A template function declaration in a header can have its definition in a separate .cpp file like a regular function.

    Because the compiler must instantiate the template at each call site, the full template definition must be available in every translation unit that uses it. Placing template definitions in separate .cpp files causes unresolved external symbol linker errors unless explicit instantiation is declared.

  3. C++20 concepts introduce dynamic type checking or type tags at runtime.

    Concepts are evaluated strictly at compile time. They generate no runtime code, no type metadata, and no performance penalty whatsoever.

6Problems

Mechanics

M1 · Writing a C++20 Concept

Write a C++20 concept MarketTick that requires type T to have an int64_t timestamp_ns() member function and a double price() member function.

Solution

template<typename T> concept MarketTick = requires(T t) { { t.timestamp_ns() } -> std::same_as<int64_t>; { t.price() } -> std::same_as<double>; };.
This concept constrains functions to types exposing the required market quote interface.

M2 · SFINAE with std::enable_if_t

Show how a function template compute_pnl was constrained to floating-point types in C++14 prior to concepts.

Solution

template<typename T, typename = std::enable_if_t<std::is_floating_point_v<T>>> T compute_pnl(T price, T cost);.
If T is not floating-point, substitution failure removes the function from the candidate set.

M3 · Constrained Auto Shorthand

How does C++20 express concept constraints using the abbreviated function template syntax?

Solution

By placing the concept name directly before auto in the parameter list: double discount(std::floating_point auto rate, std::floating_point auto tau);. This is equivalent to declaring a template with explicit requires clauses.

Proof

P1 · Static Resolution Invariance

Prove that static dispatch on a concept-constrained template produces machine code isomorphic to a manually specialized function.

Solution

Let function \(f_{\mathrm{manual}}(double)\) and template specialization \(f_{\mathrm{template}}\langle double\rangle\) contain identical token bodies. Because concept satisfaction verifies all type constraints at compile time, the compiler AST for both functions has identical nodes, types, and operator resolutions. The code generation backend maps identical ASTs to identical machine instructions.

P2 · Disambiguation via Concept Subsumption

Prove that when overload resolution compares a function constrained by Integral against one constrained by SignedIntegral, int32_t never triggers ambiguous call errors.

Solution

SignedIntegral<T> is defined as Integral<T> && std::is_signed_v<T>. By Proposition 4.4, SignedIntegral subsumes Integral. For int32_t, both constraints are satisfied, but SignedIntegral is strictly more constrained. C++20 partial ordering rules mandate selection of the more constrained overload, preventing ambiguity.

P3 · Instantiation Termination in Constrained Recursion

Prove that a recursive template metaprogram evaluating factorials at compile time terminates in finite steps when constrained by requires (N > 0) and a base specialization at N == 0.

Solution

For input integer \(N \ge 0\), each recursive instantiation decrements \(N\) by 1. Because the set of natural numbers is well-ordered under the standard ordering, the sequence \(N, N-1, \dots, 0\) reaches the base specialization \(N = 0\) in exactly \(N\) steps. At \(N = 0\), no further recursive template is referenced, terminating instantiation.

Empirical

E1 · Interpreting Lab 1 Concept Failure Diagnostics

In Lab 1, what diagnostic was produced when instantiating the pricer with str?

Solution

The compiler model emitted ConceptViolationError: type 'str' does not satisfy concept 'std::is_arithmetic_v<T>', pinpointing the failed constraint immediately rather than failing deep within the payoff math.

E2 · Functor Concept Verification in Lab 1

Why was the non-callable object "not_a_functor" rejected in Lab 1?

Solution

The pricer required PayoffFunctor<F, float>. Because strings are not invocable with a float argument, the constraint predicate returned false, rejecting the candidate before instantiation.

E3 · Execution Overhead of Generic Pricer

Why did both <double, CallPayoff> and <int64_t, CallPayoff> execute with identical batch loop efficiency?

Solution

Each instantiation created a specialized, dedicated code path where the payoff functor call was inlined directly into the loop, avoiding virtual method lookups and function pointer dispatch.

Research

R1 · Expression Templates in Matrix Mathematics

How do expression templates eliminate temporary matrix allocations in quantitative risk calculations?

Solution

In naive operator overloading, evaluating D = A + B + C creates two temporary matrices. Expression templates encode the mathematical expression into a lazy parse tree type at compile time. Evaluating element D(i, j) executes a single combined loop evaluating A(i, j) + B(i, j) + C(i, j) directly into destination memory without intermediate allocations.

R2 · Compile-Time vs Runtime Dispatch Latency

Quantify the instruction-level difference between a virtual method call and a template inlined call on modern x86-64 hardware.

Solution

A virtual call executes: mov rax, [rdi] (fetch vtable, 4-5 cycles if L1 cached), call [rax + 16] (indirect branch, risking branch predictor miss penalty of 15-20 cycles). An inlined template call executes 0 call instructions, integrating directly into surrounding instruction pipelines and enabling compiler register reuse.

R3 · Concepts vs Rust Traits and Haskell Typeclasses

How do C++20 concepts differ fundamentally from Rust traits and Haskell typeclasses regarding structural versus nominal typing?

Solution

Rust traits and Haskell typeclasses are nominal: a type satisfies a trait only if it explicitly implements it via impl Trait for Type. C++20 concepts are structural (duck-typing at compile time): any type that satisfies the syntactic and semantic requirements of the concept satisfies it automatically, without explicit registration.
