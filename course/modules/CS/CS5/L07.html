Array-of-Structures versus Struct-of-Arrays Layout

High-throughput market data engines process gigabytes of quote feeds per second. Traditional object-oriented design groups attributes into records (Array-of-Structures), scattering relevant numeric fields across memory alongside unused metadata. Struct-of-Arrays layout groups identical fields contiguously, doubling effective cache line utilization and unlocking compiler auto-vectorization across price calculations and risk pipelines.

1Memory Layouts: AoS versus SoA

Data layout in memory dictates how effectively hardware prefetchers and SIMD vector registers operate on financial streams:

Definition 7.1 (AoS and SoA Memory Organization)

In an Array-of-Structures (AoS) layout, individual composite records are stored consecutively in memory: struct Quote { double bid; double ask; uint32_t bid_sz; uint32_t ask_sz; uint64_t ts; }; Quote quotes[M];. In a Struct-of-Arrays (SoA) layout, each field is stored in its own contiguous array across all \(M\) records: struct QuotesSoA { double bids[M]; double asks[M]; uint32_t bid_sizes[M]; uint32_t ask_sizes[M]; uint64_t timestamps[M]; };. The Array-of-structs vs. struct-of-arrays layout choice determines how memory bandwidth is divided between active numerical payloads and inactive metadata during selective field traversals.

Proposition 7.2 (Cache Line Utilization Factor)

Assumption A1: Cache lines are \(L = 64\) bytes, aligned to 64-byte boundaries.
Assumption 2: A record has total size \(S\) bytes, of which \(U < S\) bytes are accessed by a selective field algorithm.
Statement: The cache line bandwidth utilization under AoS is \(\eta_{\mathrm{AoS}} = U / S\), whereas under SoA it is \(\eta_{\mathrm{SoA}} = 1.0\) (100%), reducing loaded cache lines by a factor of \(S / U\).

Proof

In AoS, each record occupies \(S\) bytes in memory. To read \(U\) bytes of interest from \(M\) records, the CPU must transfer \(M \times S\) total bytes across the memory bus, loading \(\lceil M \cdot S / L \rceil\) cache lines. Out of every \(S\) bytes loaded into L1 cache, only \(U\) bytes are used, yielding utilization \(\eta_{\mathrm{AoS}} = (M \cdot U) / (M \cdot S) = U / S < 1.0\). In SoA, the \(U\) active bytes are stored in contiguous arrays totaling \(M \times U\) bytes, loading \(\lceil M \cdot U / L \rceil\) cache lines. Every byte in each loaded line is consumed, yielding \(\eta_{\mathrm{SoA}} = 1.0\). The ratio of loaded lines is \((M \cdot S / L) / (M \cdot U / L) = S / U\). \(\blacksquare\)

2Hardware Alignment, Padding, and SIMD Vectorization

Modern compilers auto-vectorize loops only when memory can be loaded into SIMD vector registers (AVX-256 or AVX-512) in continuous chunks without gather/scatter instructions:

  • AoS SIMD Penalty: To compute midpoint prices \((bid + ask) / 2\) on AoS data, the compiler must either issue strided loads, execute permute instructions to unpack interleaved bids and asks, or fall back to scalar arithmetic.
  • SoA SIMD Alignment: In SoA, bids and asks are contiguous 64-bit float arrays. An AVX-512 load instruction (_mm512_load_pd) loads 8 contiguous doubles in a single CPU cycle. Adding the two vector registers (_mm512_add_pd) computes 8 midpoint prices simultaneously.
Proposition 7.3 (Bus Traffic Reduction on Quote Midpoints)

Assumption A1: A Quote record has size \(S = 32\) bytes (8B bid, 8B ask, 4B bid_size, 4B ask_size, 8B timestamp), and cache lines are 64 bytes.
Statement: Evaluating midpoint prices for \(M = 1024\) quotes under SoA transfers exactly 16,384 bytes across the memory bus, whereas AoS transfers 32,768 bytes, consuming exactly 2.0x less memory bandwidth.

Proof

Computing midpoints requires reading only bid (8B) and ask (8B), giving active payload \(U = 16\) bytes per quote. Total payload is \(1024 \times 16 = 16,384\) bytes. Under AoS, loading \(M = 1024\) records of 32 bytes transfers \(1024 \times 32 = 32,768\) bytes (\(32,768 / 64 = 512\) cache lines). Under SoA, reading bids (8,192B) and asks (8,192B) transfers exactly \(8,192 + 8,192 = 16,384\) bytes (\(16,384 / 64 = 256\) cache lines). The bandwidth ratio is \(32,768 / 16,384 = 2.0\). \(\blacksquare\)

Lab 1 · Array-of-structs vs struct-of-arrays cache model

Under Assumption A1 (64B cache line), evaluating midpoint prices across 1,024 quotes loads 512 cache lines in AoS (50% utilization, 16,384 bytes wasted metadata) versus 256 cache lines in SoA (100% utilization, 0 wasted bytes), reducing memory bus traffic by exactly 2.0x.

"""CS5 Lab L07: Array-of-structs (AoS) vs Struct-of-arrays (SoA) cache and bandwidth model.

Standard library only. Deterministic integer counter under Assumption A1 (64-byte cache line).
Evaluates cache lines loaded, memory bus traffic, and cache capacity efficiency when computing
midpoint prices across M order book quote records in AoS vs SoA layouts.
"""

from __future__ import annotations


def run_aos_vs_soa_cache_benchmark() -> None:
    print("CS5 L07: Array-of-Structs (AoS) vs Struct-of-Arrays (SoA) Cache Model (Assumption A1: 64B Line)")

    line_size = 64  # 64-byte hardware cache line
    m_quotes = 1024  # number of market quotes

    # Layout 1: Array-of-Structs (AoS)
    # struct Quote { double bid; double ask; uint32_t bid_sz; uint32_t ask_sz; uint64_t ts; };
    # Size: 8 + 8 + 4 + 4 + 8 = 32 bytes per Quote record.
    quote_size = 32
    line_size // quote_size  # 2 quotes per 64B cache line

    # Midpoint kernel reads only bid (8B) and ask (8B) = 16B useful payload per quote
    useful_bytes_per_quote = 16
    total_useful_payload = m_quotes * useful_bytes_per_quote

    aos_total_bytes = m_quotes * quote_size
    aos_lines_loaded = aos_total_bytes // line_size
    aos_bus_traffic = aos_lines_loaded * line_size
    aos_utilization = total_useful_payload / aos_bus_traffic

    print(f"Array-of-Structs (AoS) Layout (Quote size: {quote_size}B, M={m_quotes}):")
    print(f"  Distinct cache lines loaded: {aos_lines_loaded}")
    print(f"  Total memory bus traffic:    {aos_bus_traffic} bytes")
    print(f"  Useful payload bytes read:   {total_useful_payload} bytes")
    print(f"  Cache line utilization:      {aos_utilization:.1%}")
    print(f"  Wasted unread metadata:      {aos_bus_traffic - total_useful_payload} bytes")

    # Layout 2: Struct-of-Arrays (SoA)
    # struct QuotesSoA { double bids[M]; double asks[M]; ... };
    # bids array: 1024 * 8 = 8192 bytes; asks array: 1024 * 8 = 8192 bytes
    bids_bytes = m_quotes * 8
    asks_bytes = m_quotes * 8
    bids_lines = bids_bytes // line_size
    asks_lines = asks_bytes // line_size

    soa_lines_loaded = bids_lines + asks_lines
    soa_bus_traffic = soa_lines_loaded * line_size
    soa_utilization = total_useful_payload / soa_bus_traffic

    print(f"\nStruct-of-Arrays (SoA) Layout (Contiguous bids[] and asks[], M={m_quotes}):")
    print(f"  Distinct cache lines loaded: {soa_lines_loaded}")
    print(f"  Total memory bus traffic:    {soa_bus_traffic} bytes")
    print(f"  Useful payload bytes read:   {total_useful_payload} bytes")
    print(f"  Cache line utilization:      {soa_utilization:.1%}")
    print(f"  Wasted unread metadata:      {soa_bus_traffic - total_useful_payload} bytes")

    # Relative comparison
    line_reduction_ratio = aos_lines_loaded / soa_lines_loaded
    traffic_reduction_ratio = aos_bus_traffic / soa_bus_traffic
    print("\nComparative Layout Efficiency:")
    print(f"  Cache lines ratio (AoS / SoA): {line_reduction_ratio:.1f}x fewer cache lines loaded in SoA")
    print(f"  Bandwidth ratio  (AoS / SoA): {traffic_reduction_ratio:.1f}x less memory bus traffic in SoA")


def main() -> None:
    run_aos_vs_soa_cache_benchmark()


main()

3Where the Canon Breaks

SoA is not universally superior. When an algorithm requires full-record access (such as writing or serializing an entire quote containing bid, ask, sizes, and timestamps to disk or a network socket), SoA scatters the fields across five disparate memory arrays. Writing a single quote touches five separate cache lines, inducing write-allocate cache pollution and increasing memory bus traffic. The optimal hybrid layout is Array-of-Structs-of-Arrays (AoSoA) (or tiled SoA), where data is packed into fixed-size SIMD-width tiles (e.g. 8 or 16 quotes per struct), balancing vectorization with cache locality.

4Misconceptions

  1. Object-oriented Array-of-Structures is always more efficient because all fields of an entity are stored together.

    Storing all fields together is only efficient when all fields are accessed simultaneously. When algorithms compute over a subset of fields (e.g. price analytics ignoring trade IDs), AoS forces the CPU to load unused metadata, halving cache capacity.

  2. Struct fields in C++ are always packed contiguously with zero padding.

    Compilers insert padding bytes between struct members to satisfy hardware alignment restrictions (e.g. aligning 8-byte doubles on 8-byte addresses). Ordering struct members carelessly (e.g. interleaving 1-byte chars and 8-byte doubles) inflates struct size with wasted padding.

  3. SoA layout requires manual indexing and cannot provide clean object-oriented APIs.

    Modern C++ uses proxy reference iterators and C++20 ranges to present an SoA collection as if it were a sequence of regular objects, combining clean value semantics with optimal physical memory layout.

5Problems

Mechanics

M1 · Struct Padding and Alignment Calculation

Calculate sizeof(BadQuote) vs sizeof(GoodQuote) on x86-64 where BadQuote has members char exchange; double price; int size; and GoodQuote orders them double price; int size; char exchange;.

Solution

In BadQuote: exchange takes 1B + 7B padding (aligning price to 8B) + 8B price + 4B size + 4B tail padding = 24 bytes. In GoodQuote: 8B price + 4B size + 1B exchange + 3B tail padding = 16 bytes. Ordering from largest to smallest alignment saves 33% memory.

M2 · SoA Data Structure Definition

Write the C++ definition for an SoA order book price ladder holding up to 10,000 levels with prices, quantities, and order_counts.

Solution

struct PriceLadderSoA { std::vector<double> prices; std::vector<uint32_t> quantities; std::vector<uint16_t> order_counts; };.
Each vector allocates a contiguous buffer, permitting SIMD vectorization across price updates.

M3 · SIMD Vector Width Computation

How many 64-bit doubles fit into an AVX-512 register, and how many cache lines are required to fill it?

Solution

An AVX-512 register is 512 bits = 64 bytes wide. It holds exactly \(512 / 64 = 8\) doubles. A 64-byte AVX-512 load consumes exactly one 64-byte hardware cache line.

Proof

P1 · General Memory Bandwidth Ratio Under Field Subsetting

Prove that for any record of size \(S\) where an algorithm reads a proper subset of fields totaling \(U < S\) bytes, the memory bandwidth ratio \(\eta_{\mathrm{SoA}} / \eta_{\mathrm{AoS}} = S / U > 1\).

Solution

By Proposition 7.2, \(\eta_{\mathrm{AoS}} = U / S\) and \(\eta_{\mathrm{SoA}} = 1.0\). The ratio is \(1.0 / (U / S) = S / U\). Because \(U\) is a proper subset of fields, \(U < S\), which implies \(S / U > 1.0\), guaranteeing that SoA transfers strictly less data across the memory bus than AoS.

P2 · Minimum Cache Footprint for AoSoA Tiled Layout

Prove that in an AoSoA layout with tile width \(W = L / s\) where \(L\) is the cache line size and \(s\) is element size, selective field operations achieve 100% cache line utilization.

Solution

Let tile struct Tile contain double bids[W] followed by double asks[W]. Since \(W = L / s = 64 / 8 = 8\), bids[8] occupies exactly \(8 \times 8 = 64\) bytes, matching line size \(L\). Accessing bids loads an entire 64-byte cache line containing exclusively bid elements, consuming 100% of the loaded bytes without loading asks or metadata.

P3 · Vectorization Invariance Under Structure Transposition

Prove that computing \(\sum_{i=1}^M a_i \cdot b_i\) on AoS data requires scatter/gather or permutation instructions, whereas SoA requires zero permutations.

Solution

In AoS, elements \(a_i\) and \(b_i\) are interleaved in memory with stride \(S > s\). SIMD vector registers require adjacent packed lanes. Loading interleaved elements into packed vector registers requires either vector gather instructions (_mm256_i32gather_pd) or unpack/shuffle permutations. In SoA, \(a_i\) and \(b_i\) are contiguous, loaded via simple aligned vector loads (_mm256_load_pd) without permutations.

Empirical

E1 · Interpreting Lab 1 Cache Lines Loaded

In Lab 1, why did AoS require 512 cache lines while SoA required only 256 cache lines?

Solution

Each 32-byte Quote in AoS meant only 2 quotes fit per 64-byte line, requiring \(1024 / 2 = 512\) lines for 1,024 quotes. In SoA, only bids (128 lines) and asks (128 lines) were loaded, totaling \(128 + 128 = 256\) lines—exactly half the cache footprint.

E2 · Quantifying Unused Metadata Pollution in Lab 1

From Lab 1, how many bytes of unused metadata were transferred to CPU caches during the AoS midpoint calculation?

Solution

AoS transferred 32,768 total bytes, of which only 16,384 bytes were active bid/ask values. Exactly \(32,768 - 16,384 = 16,384\) bytes (50%) of memory traffic consisted of unused size and timestamp fields that polluted L1 cache.

E3 · Layout Selection in Order Matching Engine

In a limit order matching engine, would you store active order books in AoS or SoA, and why?

Solution

Price levels are best stored in SoA (or AoSoA) because matching algorithms repeatedly sweep contiguous prices and aggregate quantities during execution. Individual orders in the order queue are often kept in AoS because fills update or cancel specific individual orders as complete entities.

Research

R1 · AoSoA Hybrid Tiling in GPU Kernels

Why do GPU CUDA kernels and AVX-512 kernels standardize on AoSoA (Array-of-Structs-of-Arrays) layouts?

Solution

GPU threads execute in warps of 32 threads. Struct-of-Arrays-of-Arrays (AoSoA) packs 32 elements per tile. When a warp executes an instruction on field \(k\), the 32 threads access 32 contiguous memory addresses, achieving 100% coalesced memory transactions in a single memory bus cycle.

R2 · Columnar Database Storage Alignment with SoA

How does the Parquet and Arrow columnar storage model in quantitative finance directly mirror SoA memory design?

Solution

Apache Arrow and Parquet store time-series data column-by-column (SoA). When an econometric query scans only trading volumes or closing prices, the engine reads only the contiguous column chunks from disk/memory, skipping gigabytes of unreferenced columns and enabling SIMD aggregation.

R3 · Reflection and Code Generation for SoA Containers

How will C++26 static reflection simplify the automatic generation of SoA container wrappers from standard structs?

Solution

Currently, converting a struct to SoA requires manual boilerplate or macro libraries like Boost.Fusion. C++26 static reflection will inspect struct member types and names at compile time, automatically generating std::vector<Field_i> arrays and synthesized tuple accessor proxies with zero boilerplate.
