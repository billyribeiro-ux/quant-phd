Financial execution engines process millions of market messages per second. Languages relying on pointer indirection and reference semantics suffer pointer chasing, garbage collection pauses, and uncontrolled object aliasing. C++ value semantics guarantees independent object identity, deterministic stack allocation, and zero-cost ownership transfer through move semantics, eliminating heap allocation bottlenecks along critical latency paths.

1Value Semantics versus Reference Semantics

In languages like Java or Python, non-primitive variables hold references (pointers) to objects allocated on the heap. Assigning one variable to another creates an alias: both variables reference the identical underlying memory. Mutating one variable mutates the other. In contrast, C++ defaults to value semantics.

Definition 2.1 (Value Semantics)

A type exhibits value semantics (or copy-on-assignment semantics) if assignment and initialization create independent objects with separate identities such that subsequent modifications to one object leave all other objects unaffected. If \(a\) and \(b\) are instances of a value type, the assignment \(b = a\) ensures that \(a == b\) holds immediately following assignment, yet \(\&a \ne \&b\), guaranteeing disjoint storage locations.

Value semantics simplifies reasoning in multi-threaded trading engines. Because values are not shared by reference across threads, functions can consume objects by value without fear of external mutation or race conditions.

Proposition 2.2 (Independence of Value Assignment)

Assumption 1: Type \(T\) satisfies regular value semantics with deep-copy assignment.
Statement: For distinct object instances \(a, b \in T\) with \(a \ne b\), mutating the state of \(a\) via any member operation \(m(a)\) produces zero change in the observable state of \(b\).

Proof

By Definition 2.1, \(a\) and \(b\) occupy disjoint memory regions: \(\mathrm{addr}(a) \cap \mathrm{addr}(b) = \emptyset\). Because \(T\) implements deep-copy semantics, all dynamically owned buffers are distinct: \(\mathrm{heap}(a) \cap \mathrm{heap}(b) = \emptyset\). A mutating member function \(m(a)\) writes only to bytes contained in \(\mathrm{addr}(a) \cup \mathrm{heap}(a)\). Because the intersection with the storage of \(b\) is empty, the bit pattern representing the state of \(b\) remains strictly unchanged. \(\blacksquare\)

2Move Semantics and Rvalue References

Deep copying large dynamic buffers (such as price vectors or order books) imposes severe memory allocation and cache thrashing overhead. C++11 introduced rvalue references (T&&) and move semantics to distinguish temporary expressions from named lvalues.

Definition 2.3 (Lvalues, Rvalues, and Move Semantics)

An lvalue is an expression that designates an object possessing an identifiable memory address (identity) that persists beyond a single expression. An rvalue designates a temporary object or value that has no persistent identity and will be destroyed at the end of the full expression. Move semantics transfers internal resource handles (pointers, file descriptors) from an expiring rvalue to a destination object in \(\mathcal{O}(1)\) time, leaving the source in a valid but unspecified state.

std::move(x) does not move anything at runtime; it is an unconditional static cast converting an lvalue reference x into an rvalue reference static_cast<T&&>(x), enabling overload resolution to select the move constructor or move assignment operator.

Proposition 2.4 (Complexity of Resource Transfer)

Assumption 1: A container manages a dynamically allocated buffer of size \(N\) via a pointer.
Statement: Copy construction requires \(\mathcal{O}(N)\) memory allocation and byte copy operations, whereas move construction requires \(\mathcal{O}(1)\) pointer swaps.

Proof

Copy construction allocates a new buffer of \(N\) elements and executes \(N\) copy operations, taking time proportional to \(N\). Move construction reads the source pointer \(p\), copies \(p\) to the destination pointer, and sets the source pointer to nullptr. This requires exactly three machine word assignments, executing in \(\mathcal{O}(1)\) time independent of \(N\). \(\blacksquare\)

3The Rules of Zero, Three, and Five

C++ controls object lifecycle through special member functions: default constructor, copy constructor, copy assignment operator, move constructor, move assignment operator, and destructor.

  • Rule of Zero: Classes that do not directly manage raw resources should define none of the special member functions. Resource management should be delegated to standard RAII types (std::vector, std::unique_ptr, std::string).
  • Rule of Three: If a class manages a raw resource and defines a custom destructor, copy constructor, or copy assignment operator, it must define all three to prevent double-free errors.
  • Rule of Five: To support efficient move semantics, classes defining the Rule of Three should also explicitly implement or default the move constructor and move assignment operator.

Lab 1 · Value semantics and reallocation operation tracker

Tracking object lifecycle operations demonstrates that std::vector reallocations execute zero deep copies when the type provides a noexcept move constructor, but fall back to copy construction if move operations risk throwing exceptions.

"""CS5 Lab L02: Value semantics, object lifecycle, and move semantics operational model.

Standard library only. Deterministic integer operation counter. Tracks default construction,
copy construction, move construction, copy assignment, move assignment, and destruction
across dynamic container reallocations and value transfers.
"""

from __future__ import annotations


class LifecycleTracker:
    def __init__(self) -> None:
        self.default_constructs = 0
        self.copy_constructs = 0
        self.move_constructs = 0
        self.copy_assigns = 0
        self.move_assigns = 0
        self.destructs = 0

    def reset(self) -> None:
        self.default_constructs = 0
        self.copy_constructs = 0
        self.move_constructs = 0
        self.copy_assigns = 0
        self.move_assigns = 0
        self.destructs = 0


GLOBAL_TRACKER = LifecycleTracker()


class TracedValue:
    def __init__(self, value: int = 0) -> None:
        self.value = value
        self.is_moved_from = False
        GLOBAL_TRACKER.default_constructs += 1

    @classmethod
    def from_value(cls, value: int) -> TracedValue:
        return cls(value)

    def copy(self) -> TracedValue:
        GLOBAL_TRACKER.copy_constructs += 1
        return TracedValue(self.value)

    def move(self) -> TracedValue:
        GLOBAL_TRACKER.move_constructs += 1
        val = self.value
        self.is_moved_from = True
        self.value = 0
        return TracedValue(val)

    def destroy(self) -> None:
        GLOBAL_TRACKER.destructs += 1


class SimulatedVector:
    """Models std::vector dynamic reallocation behavior with geometric capacity doubling."""

    def __init__(self, use_noexcept_move: bool = True) -> None:
        self.capacity = 0
        self.data: list[TracedValue] = []
        self.use_noexcept_move = use_noexcept_move

    def push_back_lvalue(self, item: TracedValue) -> None:
        self._ensure_capacity()
        self.data.append(item.copy())

    def push_back_rvalue(self, item: TracedValue) -> None:
        self._ensure_capacity()
        self.data.append(item.move())

    def _ensure_capacity(self) -> None:
        if len(self.data) < self.capacity:
            return
        new_cap = 1 if self.capacity == 0 else self.capacity * 2
        new_data: list[TracedValue] = []
        for x in self.data:
            if self.use_noexcept_move:
                new_data.append(x.move())
            else:
                new_data.append(x.copy())
            x.destroy()
        self.data = new_data
        self.capacity = new_cap

    def clear(self) -> None:
        for x in self.data:
            x.destroy()
        self.data = []


def run_value_semantics_experiments() -> None:
    print("CS5 L02: Value Semantics and Move vs Copy Reallocation Tracker")

    # Sequence 1: push_back 8 rvalue items with noexcept move
    GLOBAL_TRACKER.reset()
    vec_move = SimulatedVector(use_noexcept_move=True)
    for i in range(8):
        v = TracedValue(i * 10)
        vec_move.push_back_rvalue(v)
        v.destroy()

    print(
        f"Push 8 rvalues (noexcept move): "
        f"moves={GLOBAL_TRACKER.move_constructs}, copies={GLOBAL_TRACKER.copy_constructs}, "
        f"destructs={GLOBAL_TRACKER.destructs}, capacity={vec_move.capacity}"
    )
    vec_move.clear()

    # Sequence 2: push_back 8 rvalue items without noexcept move (reallocations fall back to copy)
    GLOBAL_TRACKER.reset()
    vec_copy = SimulatedVector(use_noexcept_move=False)
    for i in range(8):
        v = TracedValue(i * 10)
        vec_copy.push_back_rvalue(v)
        v.destroy()

    print(
        f"Push 8 rvalues (copy on realloc): "
        f"moves={GLOBAL_TRACKER.move_constructs}, copies={GLOBAL_TRACKER.copy_constructs}, "
        f"destructs={GLOBAL_TRACKER.destructs}, capacity={vec_copy.capacity}"
    )
    vec_copy.clear()

    # Sequence 3: push_back 8 lvalue items (always deep copied at insertion)
    GLOBAL_TRACKER.reset()
    vec_lvalue = SimulatedVector(use_noexcept_move=True)
    for i in range(8):
        v = TracedValue(i * 10)
        vec_lvalue.push_back_lvalue(v)
        v.destroy()

    print(
        f"Push 8 lvalues (deep copies): "
        f"moves={GLOBAL_TRACKER.move_constructs}, copies={GLOBAL_TRACKER.copy_constructs}, "
        f"destructs={GLOBAL_TRACKER.destructs}, capacity={vec_lvalue.capacity}"
    )
    vec_lvalue.clear()


def main() -> None:
    run_value_semantics_experiments()


main()

4Where the Canon Breaks

A moved-from object in C++ is guaranteed to be in a "valid but unspecified state." This guarantee is weaker than full re-initialization. Calling member functions that require specific preconditions (such as accessing elements of a moved-from vector without checking empty()) triggers undefined behavior. Furthermore, if a programmer passes std::move(x) to a function that accepts its parameter by const&, the compiler silently falls back to copy construction without error or warning, defeating the performance optimization unnoticed.

5Misconceptions

  1. std::move performs an asynchronous data transfer or moves memory in hardware.

    std::move generates zero assembly instructions at runtime. It is purely a compile-time cast that casts an expression to an rvalue reference type (T&&), enabling the compiler to select move constructor overloads.

  2. Returning a local object by std::move(local_var) accelerates function returns.

    Wrapping a return statement with std::move disables Named Return Value Optimization (NRVO). Compilers can elide copies and moves completely by constructing the object directly in the caller's stack frame. Applying std::move forces an unnecessary move construction.

  3. A moved-from object is automatically destroyed and its memory deallocated.

    A moved-from object remains fully alive until it leaves its enclosing lexical scope. Its destructor will execute normally when the scope ends; therefore, the move constructor must leave the source object in a state where destruction is safe (e.g. setting raw pointers to nullptr).

6Problems

Mechanics

M1 · Writing a Custom Move Constructor

Given a class Buffer managing double* data_ and size_t size_, write the signature and implementation of its noexcept move constructor.

Solution

The move constructor steals the pointer and resets the source:
Buffer(Buffer&& other) noexcept : data_(other.data_), size_(other.size_) { other.data_ = nullptr; other.size_ = 0; }.
Marking it noexcept guarantees standard containers will use move operations during reallocation.

M2 · Self-Assignment in Move Assignment

Why must a move assignment operator operator=(Buffer&& other) check for self-assignment this != &other?

Solution

If code invokes buf = std::move(buf), releasing the destination buffer before stealing from other destroys the very data being moved. Checking for self-assignment prevents premature deallocation and dangling pointers.

M3 · The Rule of Zero in Practice

How does replacing a raw pointer member with std::vector<double> allow a class to adhere to the Rule of Zero?

Solution

std::vector already implements the Rule of Five correctly. When a class contains only members with valid copy, move, and destruction semantics, the compiler automatically synthesizes optimal special member functions, eliminating boilerplate and memory leaks.

Proof

P1 · Invariant of Move Construction on Resource Conservation

Prove that move construction preserves total allocated system resources without creating duplicate ownership.

Solution

Let system resources be denoted by set \(R\). Prior to move construction, source object \(S\) owns resource handle \(h \in R\). Move construction assigns \(h\) to destination object \(D\) and assigns null to \(S\). Because \(S\) no longer refers to \(h\) and \(D\) is the sole reference, the cardinality \(|R|\) is unchanged, and exactly one active owner holds \(h\), preventing double-free upon destruction.

P2 · Necessity of noexcept for Strong Exception Safety

Prove why std::vector reallocation cannot use a move constructor that may throw without violating the strong exception safety guarantee.

Solution

The strong guarantee requires that if an operation throws, program state is restored to its exact pre-call condition. Suppose std::vector moves elements \(0, \dots, k-1\) to a new buffer, and moving element \(k\) throws. Elements \(0, \dots, k-1\) in the old buffer are already in a moved-from state and cannot be deterministically un-moved if move operations throw. Thus, state cannot be restored. Hence, only noexcept moves permit moving; throwing moves force copy construction.

P3 · Amortized Cost of Dynamic Array Reallocation

Prove that pushing \(N\) elements into an initially empty geometric vector with doubling factor 2 performs at most \(2N\) total moves.

Solution

Reallocations occur at sizes \(1, 2, 4, 8, \dots, 2^k < N\). The total elements moved across all reallocations is \(\sum_{j=0}^{k} 2^j = 2^{k+1} - 1 < 2N\). Adding the \(N\) direct insertions yields fewer than \(3N\) total operations, proving \(\mathcal{O}(1)\) amortized move cost per insertion.

Empirical

E1 · Interpreting Lab 1 Operation Counts

In Lab 1, why did pushing 8 rvalues with noexcept move execute 15 moves and 0 copies?

Solution

There are 8 direct insertions. Reallocations occur when size reaches 1 (1 move), 2 (2 moves), and 4 (4 moves). Total moves = \(8 + 1 + 2 + 4 = 15\). Because move is marked noexcept, all reallocations use move constructors, resulting in 0 copies.

E2 · Reallocation with Throwing Move Constructors

In Lab 1, why did the second experiment perform 7 copies and 8 moves?

Solution

Because the move constructor was not noexcept, the container could not guarantee strong exception safety during buffer expansion. It fell back to copy construction during reallocations (\(1 + 2 + 4 = 7\) copies) while still moving the incoming temporary rvalues (8 moves).

E3 · Lvalue Insertions vs Rvalue Insertions

In Lab 1, why did pushing 8 lvalues execute 8 copies and 7 moves?

Solution

Because the arguments were persistent lvalues, inserting them into the vector required deep copies (8 copies). However, during buffer reallocations, existing vector elements were transferred via move semantics (7 moves).

Research

R1 · Pass-by-Value with std::move Idiom

When is passing a parameter by value and moving it into a member variable superior to overloading on const& and &&?

Solution

For a constructor taking \(k\) independent arguments, overloading on lvalues and rvalues requires \(2^k\) separate overload signatures. Accepting parameters by value requires only 1 signature. Callers passing rvalues incur 1 move into the parameter and 1 move into the member (2 cheap moves), eliminating combinatorial boilerplate.

R2 · Small String Optimization (SSO) and Value Semantics

How does Small String Optimization (SSO) affect the performance of value semantics for short financial tickers?

Solution

SSO stores strings up to 15 or 22 characters directly in an internal stack buffer inside the string object, avoiding heap allocation. For short strings like equity tickers ("AAPL", "MSFT"), copying and moving take identical fixed-word memory copies, completely eliminating dynamic allocation latency.

R3 · Relocation Semantics in Future C++

What is the limitation of C++ move semantics compared to destructive relocation (as in Rust), and how would trivial relocation improve vector resizing?

Solution

C++ move semantics leaves the moved-from source object alive, requiring its destructor to execute later. Trivial relocation allows moving objects via raw memcpy without running destructors on the old storage, reducing vector resizing to a single bulk memory transfer.
