Quantitative code relies on deterministic state transitions. A financial calculation that accidentally reads or mutates an ambient global variable can produce corrupt valuations, catastrophic order sizing, or unreproducible backtest results. Understanding the exact lexical scope resolution rule (LEGB), parameter binding semantics, and closure capture guarantees that computational procedures remain pure, modular, and mathematically verifiable.

1Functions, Environments, and Lexical Scope

A function in Python is a first-class object that bundles executable bytecode with a reference to its enclosing global environment. When a function is called, the interpreter creates a new local execution frame containing its local namespace.

Definition 1.1 (Function Scope and Namespaces)

A namespace is a mapping from symbolic variable names (strings) to Python objects. The function scope refers to the textual region of a Python program where a namespace is directly accessible without explicit dot notation. Python evaluates variable references using the lexical LEGB rule: resolving names in the Local (L) scope first, then Enclosing (E) function scopes from inner to outer, then the Global (G) module scope, and finally the Built-in (B) namespace.

Theorem 1.1 (Local Assignment Scope Invariant)

If a variable name is bound anywhere within a function body by an assignment statement \(=\), an augmented assignment \(\text{+=}\), or a formal parameter definition, without an explicit global or nonlocal declaration, the name is treated as belonging strictly to the local scope of that function throughout the entire function body. Referencing the name prior to its assignment within that local frame raises an UnboundLocalError rather than resolving to an outer scope.

Proof

By the Python language specification (PSF Language Reference, Section 4.2), variable scope is resolved statically at code compilation time, not dynamically at runtime. When the compiler analyzes a code block, any name binding operation marks the name as a local variable for the entire code object. During execution, name resolution for marked local variables targets the local fast-access array (LOAD_FAST bytecode instruction). If the slot has not yet been populated by an assignment at the point of evaluation, execution halts and raises UnboundLocalError.

Example 1.1 (LEGB Lookup and Closure State)

Consider a discounting factory that generates valuation functions for a fixed discount factor \(\beta = \frac{1}{1 + r}\):

def make_pricer(annual_rate: float):
    discount_factor = 1.0 / (1.0 + annual_rate)
    def pricer(cash_flow: float) -> float:
        return cash_flow * discount_factor
    return pricer

The inner function pricer captures discount_factor from its enclosing scope. The returned function object retains this binding in its __closure__ attribute even after make_pricer has returned.

Remark 1.1 (Closures in Financial Engineering)

Ramalho (2021) emphasizes that a closure is a function that retains the bindings of the free variables that exist when the function is defined, so that they can be used later when the function is invoked and the defining scope is no longer available. In financial programming, closures allow parameterizing pricing kernels and risk models cleanly without resorting to mutable global state.

Lab 1 · Variable Shadowing, Closures, and Parameter Binding

Verifies that variable assignment inside a local function frame creates a local binding that shadows outer variables without altering the global scope, and that inner functions capture enclosing state to form stateful closures.

"""CS1 lab L01: Function definitions, lexical scope, and closure bindings.

Standard library only. Demonstrates the LEGB (Local, Enclosing, Global, Built-in) rule,
variable shadowing, and closure capture.
SIMULATED toy discount factors and multipliers.
"""

from __future__ import annotations

from collections.abc import Callable

# Global scope
DISCOUNT_RATE: float = 0.05


def inspect_scope_shadowing(val: float) -> tuple[float, float]:
    """Demonstrate local variable shadowing of global scope."""
    # Local variable shadows global DISCOUNT_RATE
    DISCOUNT_RATE: float = val  # noqa: N806
    local_val = DISCOUNT_RATE
    return local_val, globals()["DISCOUNT_RATE"]


def make_accumulator(initial_cash: float) -> Callable[[float], float]:
    """Return a closure holding enclosing state."""
    balance: float = initial_cash

    def transact(cash_flow: float) -> float:
        nonlocal balance
        balance += cash_flow
        return balance

    return transact


def compound_discount(cash: float, rate: float, periods: int) -> float:
    """Compute simple discrete discounting: cash / (1 + rate)^periods."""
    if periods < 0:
        raise ValueError("periods must be non-negative")
    factor = 1.0
    for _ in range(periods):
        factor *= 1.0 + rate
    return cash / factor


def main() -> None:
    # 1. Global vs local shadowing
    local_rate, global_rate = inspect_scope_shadowing(0.12)
    print(f"global before: {DISCOUNT_RATE:.4f}")
    print(f"local inside: {local_rate:.4f}")
    print(f"global read via globals(): {global_rate:.4f}")
    print(f"shadowing does not mutate global: {DISCOUNT_RATE == 0.05}")

    # 2. Closure enclosing scope
    acc = make_accumulator(1000.0)
    b1 = acc(250.0)
    b2 = acc(-150.0)
    b3 = acc(50.0)
    print(f"closure step 1: balance = {b1:.1f}")
    print(f"closure step 2: balance = {b2:.1f}")
    print(f"closure step 3: balance = {b3:.1f}")

    # 3. Parameter binding and compound discount calculation
    pv = compound_discount(1102.5, 0.05, 2)
    print(f"discounted cash flow: {pv:.2f}")
    print(f"exact match to expected 1000.00: {abs(pv - 1000.0) < 1e-9}")


main()
global before: 0.0500
local inside: 0.1200
global read via globals(): 0.0500
shadowing does not mutate global: True
closure step 1: balance = 1250.0
closure step 2: balance = 1100.0
closure step 3: balance = 1150.0
discounted cash flow: 1000.00
exact match to expected 1000.00: True

The lab confirms the LEGB rule: assigning to DISCOUNT_RATE locally leaves the module-level global variable untouched at 0.0500. Furthermore, the accumulator closure maintains private mutable state across invocations, correctly updating the balance from 1000.0 to 1150.0.

2Where the canon breaks

In introductory computer science, programmers are frequently taught that variables resolve dynamically up the call stack, or that a function can read an ambient global configuration variable if it does not write to it. In institutional production systems, relying on global configuration variables breaks under concurrency and multiprocessing: worker threads or subprocesses either inherit stale copies or experience race conditions. Best practices in quantitative development require explicit dependency injection via function arguments or pure functional closures.

3Misconceptions

  1. “Python checks variable scope at runtime based on the most recent assignment executed.”

    Python resolves variable scope statically at compile time. If a function contains an assignment to a variable anywhere in its body, that name is tagged as local throughout the function. Attempting to read it before the assignment raises UnboundLocalError, even if an identically named global variable exists.

  2. “Default argument values are re-evaluated each time a function is called.”

    Default parameter expressions are evaluated exactly once when the function definition statement is executed. If a mutable object (such as a list or dict) is used as a default parameter, all invocations share the identical instance, leading to state leakage across unrelated calls.

  3. “Modifying a parameter inside a function cannot affect the caller.”

    Python uses call-by-object-sharing. Rebinding a parameter name inside a function does not affect the caller, but calling mutating methods on a mutable passed object (such as list.append()) mutates the underlying object in place, directly modifying the caller's data.

4Problem set

Mechanics

M1 · Tracing LEGB Scope

Given the code below, determine the exact value printed when outer() is executed:

x = 10
def outer():
    x = 20
    def inner():
        nonlocal x
        x += 5
        return x
    return inner() + x
Solution

Inside outer(), x is initialized to 20. The inner() function declares nonlocal x, binding it to outer's local variable. Executing x += 5 mutates this variable from 20 to 25 and returns 25. Then inner() + x evaluates to \(25 + 25 = 50\). The global variable x = 10 remains unaffected.

M2 · Default Parameter Binding

A developer writes def record_trade(trade_id: str, log: list[str] = []) -> list[str]: log.append(trade_id); return log. What is returned after calling record_trade("T1") followed by record_trade("T2")?

Solution

Because default arguments are evaluated once at definition time, both calls share the same list instance. The first call appends "T1" and returns ["T1"]. The second call appends "T2" to the same list and returns ["T1", "T2"]. To prevent this, the default should be None with an explicit if log is None: log = [] guard.

M3 · Scope Resolution with Shadowing

Explain why the following function raises an UnboundLocalError when called:

rate = 0.05
def adjust():
    print(rate)
    rate = 0.06
Solution

Because rate = 0.06 assigns to rate in the function body, the Python compiler marks rate as a local variable for the entire scope of adjust(). When print(rate) executes on line 2, the local variable has not yet been assigned a value, causing the runtime to raise UnboundLocalError: local variable 'rate' referenced before assignment.

Proof

P1 · Invariance of Caller Bindings under Local Rebinding

Prove that rebinding a local parameter name \(x\) inside a function \(f(x)\) cannot alter the caller's binding in the calling frame.

Solution

Let frame \(F_c\) be the caller frame containing namespace mapping \(\sigma_c: \text{id} \to \text{Obj}\). When \(f\) is called with argument \(a\), a new activation frame \(F_f\) is created with namespace \(\sigma_f\), initializing \(\sigma_f(x) = \sigma_c(a)\). An assignment statement \(x = v\) within \(f\) updates the mapping \(\sigma_f(x) \leftarrow v\). Because \(\sigma_c\) and \(\sigma_f\) are disjoint symbol tables residing in distinct execution frames, \(\sigma_c(a)\) remains unchanged.

P2 · Closure Cell Lifetime

Prove that an inner function referencing an enclosing variable maintains a valid reference even after the outer function's execution frame has terminated.

Solution

When the compiler detects a variable in an enclosing scope referenced by an inner function, it allocates a cell object on the heap rather than a stack-allocated frame slot. Both the outer function's local frame and the inner function's code object hold references to this cell object. When the outer frame exits and is deallocated, the cell object's reference count remains positive because it is referenced in the inner function's __closure__ tuple. Thus the binding persists.

P3 · Termination of Linear Tail Recursion

Prove by mathematical induction that a recursive counting function \(f(n)\) defined by \(f(0) = 0\) and \(f(n) = 1 + f(n - 1)\) for \(n \in \mathbb{N}\) terminates in exactly \(n + 1\) frame allocations and returns \(n\).

Solution

Base case: For \(n = 0\), the condition \(n == 0\) matches immediately, returning 0 after 1 frame allocation. Inductive step: Assume the property holds for \(k \ge 0\). For \(n = k + 1\), the function invokes \(f(k)\), which by hypothesis makes \(k + 1\) allocations and returns \(k\). Adding the initial call gives \((k + 1) + 1\) allocations, and the returned value is \(1 + k = k + 1\). By induction, the proposition holds for all \(n \in \mathbb{N}\).

Empirical

E1 · Measuring Closure State Integrity

Write a simulation that instantiates 1,000 independent closure accumulators, executes 10 random deposits on each, and verifies that no cross-talk occurs between closure instances.

Solution

Construct a factory function returning an accumulator closure. Loop 1,000 times, creating closures with distinct seed balances. For each closure, record its transaction history and assert that the final balance matches the sum of the initial balance and its specific deposits. Running this test confirms that each closure maintains an isolated heap cell with zero cross-instance pollution.

E2 · Disassembly Inspection of Name Resolution

Inspect the Python bytecode generated for local versus global variable access using the dis module and explain the operational difference.

Solution

Disassembling a function that reads a local variable reveals the LOAD_FAST opcode, which indexes directly into a pre-allocated array of pointers on the execution frame with \(O(1)\) memory access. Disassembling global access reveals LOAD_GLOBAL, which performs a hash table lookup in the global module dictionary followed by the built-in dictionary. Local access is significantly faster.

E3 · Recursion Depth Limit

Determine empirically the default Python recursion limit via sys.getrecursionlimit() and describe the exception raised when exceeded.

Solution

Calling sys.getrecursionlimit() in CPython returns 1,000 by default. Defining a recursive function with no base case and invoking it causes the interpreter to allocate frames until the recursion depth limit is reached, at which point CPython raises RecursionError: maximum recursion depth exceeded to prevent an operating system stack overflow.

Research

R1 · Pure Functional Architecture in Financial Pipelines

Analyze the software architecture tradeoffs of pure functions versus stateful closures when constructing real-time risk calculation pipelines.

Solution

Pure functions take all inputs explicitly and return new outputs without side effects, providing trivial testability, safe concurrency across CPU threads, and straightforward memoization. However, when streaming tick data arrives at high frequency, allocating new data structures on every tick incurs garbage collection overhead. Closures or specialized accumulators encapsulate rolling state efficiently while preserving clean interface boundaries.

R2 · Global Interpreter Lock and Shared State

Evaluate how Python's module-level global variables interact with multithreading under CPython's Global Interpreter Lock (GIL).

Solution

Although the GIL prevents simultaneous execution of Python bytecode across multiple OS threads, it does not guarantee atomic multi-step operations. If multiple threads read, modify, and write to a global dictionary or counter, bytecode instructions can be preempted between the read and write steps, resulting in race conditions and lost updates. Synchronization primitives (locks) or thread-local storage are required.

R3 · Compilation Optimizations for Local Namespaces

Explain how modern Python JIT and bytecode compilers exploit static lexical scoping to optimize arithmetic performance.

Solution

Because lexical scoping guarantees that local names cannot be intercepted or modified by external modules, compilers can safely eliminate dead stores, unroll static loops, and register-allocate variables. In contrast, global variables can be modified dynamically at any time by imported code, forcing compilers to emit deoptimization guards and re-fetch pointers from dictionaries.

6Retrieval quiz

  1. What does LEGB stand for in Python name resolution?

    Options

    LEGB describes the strict lookup order: Local scope first, then Enclosing functions, then Global module, then Built-in.

  2. What happens when a variable is assigned inside a function without a global or nonlocal keyword?

    Options

    Python marks the variable as local for the entire function at compile time (Theorem 1.1).

  3. Which keyword explicitly allows an inner function to rebind a variable in an outer enclosing function?

    Options

    The nonlocal statement causes the listed identifiers to refer to previously bound variables in the nearest enclosing scope excluding globals.

  4. When are default parameter expressions evaluated in Python?

    Options

    Default parameter values are evaluated once at function definition time, which is why mutable defaults retain state across calls.

  5. What exception is raised when reading a local variable before its assignment statement inside a function?

    Options

    UnboundLocalError is a subclass of NameError raised specifically when a local variable is referenced before being bound.

  6. What is the default CPython recursion depth limit reported by sys.getrecursionlimit()?

    CPython sets the default maximum recursion limit to 1000.

  7. Where are free variables captured by a closure stored on a function object?

    Options

    Closures store references to outer scope variables in cell objects within the function's __closure__ tuple.

  8. Does rebinding a parameter variable name inside a function mutate the object passed by the caller?

    Options

    Rebinding a parameter name simply points the local symbol to a new object, leaving the caller's binding and original object unchanged.
