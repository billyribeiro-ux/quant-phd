Quantitative code directly manages capital. A subtle calculation bug—such as an off-by-one index error in return lags or inverted signs in yield discounting—can destroy a fund's performance before it is detected in live trading. Unit tests provide automated, repeatable mathematical verification: holding every function to its formal contract, asserting numerical invariants, and ensuring regressions are caught at the development gate before deployment.

1Automated Testing, Invariants, and Test Harnesses

Automated test frameworks execute isolated test functions to verify that software components conform to their formal specifications. In modern Python, pytest is the standard testing framework.

Definition 1.1 (Unit Test)

A unit test is an automated procedure that invokes an isolated, individual unit of software (such as a function or class method) under controlled inputs and asserts that its observed outputs, state changes, or exception behaviors strictly match expected values. In pytest, unit tests are plain functions prefixed with test_ residing in files named test_*.py, using plain Python assert statements.

Theorem 1.1 (Assertion Invalidation Invariant)

An assertion assert condition, message succeeds quietly if bool(condition) evaluates to True. If bool(condition) evaluates to False, the runtime immediately raises an AssertionError containing the evaluated expression details. A test function passes if and only if it terminates normally without raising an unhandled exception or AssertionError.

Proof

By the Python assert statement specification (PSF Language Reference, Section 7.3), executing assert expr, msg is bytecode-equivalent to: \[ \text{if not (expr): raise AssertionError(msg)} \] The pytest test runner wraps each collected test execution in a protective try-except block. If an AssertionError is caught, pytest records a test failure and inspects the abstract syntax tree (AST) via assertion rewriting to report exact operand sub-values. If any other unhandled exception is caught, it records an error. If execution exits without an exception, the test is marked as passed.

Example 1.1 (Testing Floating-Point Invariants and Exceptions)

In quantitative finance, comparing floating-point numbers requires tolerances rather than exact equality. In pytest:

import math
import pytest

def test_return_compounding():
    prices = [100.0, 105.0, 110.25]
    r = simple_return(prices)
    # Check multi-period compounding identity
    compounded = (1.0 + r[0]) * (1.0 + r[1])
    assert math.isclose(compounded, 1.1025, rel_tol=1e-12)

def test_negative_price_raises():
    with pytest.raises(ValueError, match="strictly positive"):
        simple_return([100.0, -50.0])

The pytest.raises context manager verifies that the expected exception is raised, failing the test if the function succeeds silently.

Remark 1.1 (Testing Catching Regressions)

Ramalho (2021) emphasizes that a comprehensive test suite catches regressions early when libraries are refactored or updated. In Atlas milestones, every milestone's test suite remains active in continuous integration to verify that subsequent milestones never break prior delivered functionality.

Lab 1 · Automated Unit Testing with pytest and Assertions

Verifies that unit test functions evaluate mathematical equality using math.isclose, catch expected domain exceptions using pytest.raises, and report assertion failures when an invariant is violated.

"""CS1 lab L06: Unit testing with pytest assertions and exception checks.

Uses pytest to demonstrate test fixtures, invariant assertions, and pytest.raises.
SIMULATED financial instruments.
"""

from __future__ import annotations

import math
from collections.abc import Callable

import pytest


def calculate_yield(face: float, price: float, maturity: float) -> float:
    """Calculate annualized zero-coupon yield: (face / price)**(1/maturity) - 1."""
    if price <= 0.0 or face <= 0.0:
        raise ValueError("Price and face value must be strictly positive")
    if maturity <= 0.0:
        raise ValueError("Maturity must be strictly positive")
    return float((face / price) ** (1.0 / maturity) - 1.0)


# --- Unit Tests ---


def test_calculate_yield_positive() -> None:
    """Check standard yield value on annual zero."""
    y = calculate_yield(100.0, 95.0, 1.0)
    expected = 100.0 / 95.0 - 1.0
    assert math.isclose(y, expected, rel_tol=1e-12)


def test_calculate_yield_multiyear() -> None:
    """Check compounding over multiyear maturity."""
    y = calculate_yield(100.0, 80.0, 2.0)
    expected = (100.0 / 80.0) ** 0.5 - 1.0
    assert math.isclose(y, expected, rel_tol=1e-12)


def test_calculate_yield_invalid_price() -> None:
    """Check that nonpositive price raises ValueError with pytest.raises."""
    with pytest.raises(ValueError, match="strictly positive"):
        calculate_yield(100.0, -95.0, 1.0)


def test_calculate_yield_invalid_maturity() -> None:
    """Check that nonpositive maturity raises ValueError with pytest.raises."""
    with pytest.raises(ValueError, match="strictly positive"):
        calculate_yield(100.0, 95.0, 0.0)


def test_deliberate_assertion_failure() -> None:
    """Deliberately failing assertion to inspect failure reporting."""
    assert 2 + 2 == 5, "deliberate math mismatch"


def main() -> None:
    # Run test suite programmatically
    suite: list[tuple[str, Callable[[], None]]] = [
        ("test_calculate_yield_positive", test_calculate_yield_positive),
        ("test_calculate_yield_multiyear", test_calculate_yield_multiyear),
        ("test_calculate_yield_invalid_price", test_calculate_yield_invalid_price),
        ("test_calculate_yield_invalid_maturity", test_calculate_yield_invalid_maturity),
    ]

    passed = 0
    for name, test_func in suite:
        try:
            test_func()
            passed += 1
            print(f"RUN {name}: PASS")
        except Exception as exc:
            print(f"RUN {name}: FAIL ({exc})")

    print(f"passed: {passed} of {len(suite)}")

    # Verify that the failing test raises AssertionError
    caught_assertion = False
    try:
        test_deliberate_assertion_failure()
    except AssertionError as exc:
        caught_assertion = True
        print(f"caught expected AssertionError: '{exc}'")

    print(f"deliberate failure caught: {caught_assertion}")


main()
RUN test_calculate_yield_positive: PASS
RUN test_calculate_yield_multiyear: PASS
RUN test_calculate_yield_invalid_price: PASS
RUN test_calculate_yield_invalid_maturity: PASS
passed: 4 of 4
caught expected AssertionError: 'deliberate math mismatch'
deliberate failure caught: True

The lab confirms Theorem 1.1: all four passing test functions execute cleanly without raising exceptions, while the deliberate failure function triggers an AssertionError with its designated error message, demonstrating how pytest isolates and reports test failures.

2Where the canon breaks

In basic tutorials, developers often test code manually by calling print statements and eyeballing terminal output. In quantitative asset management, manual testing provides zero regression protection: a subtle formula error in a 1,000-line module will never be spotted visually across hundreds of assets. Automated test runners running in continuous integration gates are required to guarantee that every commit satisfies all mathematical and operational invariants.

3Misconceptions

  1. “Floating-point numbers can be tested for exact equality using assert a == b.”

    Binary floating-point arithmetic (IEEE 754) introduces minor rounding errors in least significant bits (e.g. 0.1 + 0.2 != 0.3). Numerical tests must use math.isclose(a, b, rel_tol=1e-12) or pytest.approx(a) with explicit tolerances.

  2. “Writing unit tests requires subclassing unittest.TestCase.”

    Modern pytest allows writing plain Python functions starting with test_ and standard assert statements. It uses AST assertion rewriting to report rich diffs without requiring boilerplate test case classes.

  3. “Passing tests prove that code is completely free of bugs.”

    Tests only prove the absence of defects for the specific inputs and invariants tested. Comprehensive test suites combine boundary edge cases, invariant testing, and property-based seed sweeps to maximize defect detection.

4Problem set

Mechanics

M1 · Writing a Parameterized Test

Show how to write a parameterized test in pytest that verifies is_positive(x) across inputs 1.0, 5.5, and 100.0.

Solution

Using the @pytest.mark.parametrize decorator:

import pytest

@pytest.mark.parametrize("val", [1.0, 5.5, 100.0])
def test_is_positive(val: float):
    assert val > 0.0

pytest executes the test function once for each value in the list, reporting individual pass/fail results.

M2 · Testing Multiple Exception Types

Write a test function that asserts that passing None to simple_return() raises TypeError, and passing a list of length 1 raises ValueError.

Solution

Using separate pytest.raises context blocks:

import pytest

def test_invalid_return_inputs():
    with pytest.raises(TypeError):
        simple_return(None)
    with pytest.raises(ValueError):
        simple_return([100.0])

Both exception checks must be satisfied for the test to pass.

M3 · Tolerance Selection in Price Ratios

Why is a relative tolerance of 1e-12 appropriate for checking return invariants in 64-bit IEEE floating-point arithmetic?

Solution

IEEE 754 double-precision floats provide 53 bits of mantissa, corresponding to approximately 15 to 17 significant decimal digits of precision (machine epsilon \(\epsilon \approx 2.22 \times 10^{-16}\)). A tolerance of 1e-12 accommodates up to a few thousand cumulative rounding operations while still catching any substantive algebraic error.

Proof

P1 · Test Independence Invariant

Prove that running test functions in arbitrary order produces identical pass/fail outcomes if and only if no test modifies global mutable state.

Solution

Let \(\sigma_0\) be the initial global system state. Let test \(T_i\) be a state transition \(\sigma \to \sigma'\) followed by an assertion check. If each \(T_i\) is pure (meaning \(\sigma' = \sigma\)), then for any permutation \(\pi\) of tests, the state before test \(\pi(k)\) is identically \(\sigma_0\). If any test mutates global state such that \(\sigma' \neq \sigma\), the input state for subsequent tests depends on \(\pi\), violating test independence and order-invariance.

P2 · Non-False-Positive Guarantee of Exception Assertions

Prove that with pytest.raises(E): block cannot pass if block terminates without raising an exception.

Solution

The context manager enters with __enter__. If the guarded body finishes without an exception, __exit__(None, None, None) is called. In this exit handler, because the received exception argument is None, the context manager explicitly raises Failed: DID NOT RAISE <class E>, failing the test. Hence, zero unraised executions can pass.

P3 · AST Assertion Rewriting Transparency

Prove that pytest's assertion rewriting preserves the original boolean evaluation semantics of the assertion expression.

Solution

During test module import, pytest's import hook intercepts the AST. For any Assert(test, msg) node, it replaces the node with an expression that evaluates each sub-expression of test into temporary variables, evaluates the boolean condition, and constructs an explanatory string only if the condition evaluates to falsy. Because sub-expressions are evaluated in standard left-to-right short-circuiting order, side-effects and boolean results remain identical to un-rewritten execution.

Empirical

E1 · Measuring Test Suite Execution Time

Execute pytest with the --durations=5 flag on a numerical test suite to identify the five slowest test cases.

Solution

Running pytest --durations=5 profiles each test execution, printing a breakdown of the slowest setup, call, and teardown durations. In fast quantitative unit test suites, individual unit tests should finish in under 10 milliseconds, keeping total suite execution under a few seconds.

E2 · Seed-Based Deterministic Test Generation

Construct a test generator that runs a returns invariant test across 50 consecutive seeds (0 to 49) and confirm all 50 seeds pass.

Solution

Use a loop or parameterized fixture over range(50). For each seed, invoke make_instance(seed) to obtain a reproducible price series, compute simple and log returns, and assert the invariant math.isclose(ell[t], math.log(1 + r[t]), rel_tol=1e-12). All 50 runs pass with zero failures.

E3 · Mutation Testing Concepts

Deliberately introduce an off-by-one bug into a return calculation function (computing P[t] / P[t] - 1) and observe which unit test detects it.

Solution

The mutated function returns all zeros (since \(P_t / P_t - 1 = 0\)). The unit test checking return values against expected reference prices immediately catches the defect, raising AssertionError: simple_return mismatch at index 0: got 0.0, expected 0.025, killing the mutant.

Research

R1 · Test-Driven Development (TDD) in Quantitative Research

Analyze how writing unit tests before implementation impacts mathematical correctness and algorithmic clarity in financial modeling.

Solution

TDD forces the researcher to define exact mathematical specifications, domain boundaries, error behaviors, and precision requirements before writing production code. This prevents ambiguous function contracts, clarifies edge cases (empty data, zero prices), and creates an instant regression harness that supports confident refactoring and optimization.

R2 · Property-Based Testing vs. Example-Based Testing

Compare traditional example-based unit testing with property-based testing (using libraries like Hypothesis) for pricing engines.

Solution

Example-based testing asserts known answers on hand-crafted price paths (e.g. 100 to 105). Property-based testing generates thousands of pseudo-random price paths across extreme values (huge magnitudes, tiny fractions, infinite precision), asserting invariant laws (such as put-call parity or return additivity). Property-based testing excels at uncovering corner-case numeric underflow or division-by-zero vulnerabilities.

R3 · Mocking and Isolation in Execution Venues

Evaluate the risks of over-mocking exchange APIs during quantitative integration testing.

Solution

Mocking external order gateways isolates units from network dependencies during unit testing. However, if mock behavior diverges from real exchange matching engines (e.g. failing to model order rejection latency, partial fills, or race conditions), the unit test suite can pass completely while the live strategy fails catastrophic execution checks. End-to-end integration tests on recorded market feeds are essential.

  1. What prefix must test functions have for pytest to automatically discover and run them?

    Options

    By default, pytest discovers all functions with the test_ prefix in files matching test_*.py.

  2. How does pytest verify that an expression evaluates to True inside a test function?

    Options

    pytest rewrites plain assert statements at import time to provide rich failure diffs without boilerplate methods.

  3. Which context manager is used in pytest to assert that a block of code raises a specific exception?

    Options

    pytest.raises(ExceptionClass) asserts that the enclosed block raises the specified exception type.

  4. Why should financial float equality assertions use math.isclose rather than ==?

    Options

    IEEE 754 floating point arithmetic introduces minor binary rounding differences, necessitating tolerance-based comparisons.

  5. What decorator enables running a single test function across multiple test input sets in pytest?

    Options

    @pytest.mark.parametrize executes the decorated test once for each item in the provided collection.

  6. What happens if a test wrapped in with pytest.raises(ValueError): executes without raising any exception?

    Options

    If the expected exception is not raised, pytest.raises raises a failure exception because the expected error was not observed.

  7. If a test function executes five assertions and all five evaluate to True, how many unhandled exceptions are raised?

    A successful assertion evaluates quietly without raising an exception, so exactly 0 exceptions are raised.

  8. What pytest command-line flag stops test execution immediately upon the first failure?

    Options

    The -x flag tells pytest to exit immediately on first test failure.
