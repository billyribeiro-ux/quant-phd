Quantitative libraries require clean abstraction boundaries: pricing models, risk engines, and execution venues must be swappable without rewriting calling code. In traditional object-oriented architectures, tight coupling to deep class hierarchies causes fragile code. Structural protocols provide static type safety alongside Python's dynamic duck typing: any class that satisfies the required interface contract is accepted without explicit inheritance.

1Object Encapsulation and Method Dispatch

In Python, everything is an object: every object possesses an identity, a type, and internal state. Classes act as factories for creating instances that bundle state with behavior.

Definition 1.1 (Classes and Objects)

Classes and objects form the core of Python's object model. A class defines a user-defined type, encapsulating attributes (data state) and methods (functions bound to the instance via the first parameter self). Instance creation invokes __new__() to allocate memory and __init__() to initialize state. Method dispatch traverses the class hierarchy defined by the Method Resolution Order (MRO).

Definition 1.2 (Structural Protocols and Duck Typing)

A structural protocol (formalized via typing.Protocol) defines an interface contract based on the presence of specific methods and attributes rather than nominal inheritance. An object conforms to a structural protocol if its public interface includes all attributes and methods declared by the protocol with compatible signatures. This provides static type checking for duck typing: "if it walks like a duck and quacks like a duck, it is a duck."

Theorem 1.1 (Structural Subtyping Conformance Invariant)

Let \(\mathcal{P}\) be a structural protocol defining method signatures \(\{m_1, \dots, m_k\}\). Let \(\mathcal{C}\) be any concrete class whose namespace contains callable attributes \(\{m_1, \dots, m_k\}\) with covariant return types and contravariant parameter types relative to \(\mathcal{P}\). Then \(\mathcal{C}\) is a subtype of \(\mathcal{P}\) (\(\mathcal{C} \le \mathcal{P}\)) in the type system, and an instance \(c \in \mathcal{C}\) is valid wherever \(\mathcal{P}\) is expected, regardless of whether \(\mathcal{C}\) explicitly inherits from \(\mathcal{P}\) or imports \(\mathcal{P}\).

Proof

By the structural subtyping specification (PSF Language Reference, Section 3.3; Ramalho, 2021, Ch. 13), type checking against a Protocol evaluates the structural attributes of candidate classes. When a class defines attributes matching the protocol's required names and signatures, the type checker statically accepts the assignment without requiring \(\mathcal{C}\) to appear in the nominal inheritance DAG of \(\mathcal{P}\). If decorated with @runtime_checkable, isinstance(c, \mathcal{P}) dynamically checks attribute presence and callability via getattr(), returning True.

Example 1.1 (Valuation Protocol Without Subclassing)

Consider a portfolio pricer that accepts any object with a price(spot: float) -> float method:

from typing import Protocol, runtime_checkable

@runtime_checkable
class Pricer(Protocol):
    def price(self, spot: float) -> float: ...

class CustomSwap:
    def __init__(self, fixed_rate: float):
        self.fixed_rate = fixed_rate
    def price(self, spot: float) -> float:
        return spot - self.fixed_rate * 100.0

Because CustomSwap implements price, isinstance(CustomSwap(0.03), Pricer) evaluates to True even though CustomSwap never mentions Pricer.

Remark 1.1 (Composition Over Inheritance)

Ramalho (2021) emphasizes that deep nominal inheritance hierarchies in financial software create tight coupling and fragile base classes. Structural protocols combined with object composition allow constructing modular trading systems where analytics engines, order routers, and risk monitors interact through explicit behavioral contracts.

Lab 1 · Class Encapsulation and Structural Protocol Verification

Verifies that independent classes satisfying a structural protocol interface can be checked dynamically with isinstance and invoked polymorphically without nominal inheritance.

"""CS1 lab L03: Object-oriented programming and structural protocols.

Standard library only. Tests class encapsulation, instance methods, and structural
conformance to a Protocol without nominal inheritance.
SIMULATED valuation models.
"""

from __future__ import annotations

from typing import Protocol, runtime_checkable


@runtime_checkable
class Pricer(Protocol):
    """Structural protocol defining pricing behavior."""

    def price(self, spot: float) -> float:
        """Compute fair value given underlying spot price."""
        ...


class LinearPricer:
    """Nominal class implementing forward payoff."""

    def __init__(self, multiplier: float, basis: float) -> None:
        self.multiplier = multiplier
        self.basis = basis

    def price(self, spot: float) -> float:
        return self.multiplier * spot + self.basis


class DiscountedCashFlow:
    """A completely independent class that never mentions Pricer or inherits from it."""

    def __init__(self, discount_factor: float) -> None:
        self.discount_factor = discount_factor

    def price(self, spot: float) -> float:
        return spot * self.discount_factor


def execute_valuation(pricer: Pricer, spot: float) -> float:
    """Polymorphic valuation function accepting any structural pricer."""
    return pricer.price(spot)


def main() -> None:
    linear = LinearPricer(1.5, -10.0)
    dcf = DiscountedCashFlow(0.95)

    # 1. Structural runtime protocol check
    print(f"LinearPricer conforms to Pricer: {isinstance(linear, Pricer)}")
    print(f"DiscountedCashFlow conforms to Pricer: {isinstance(dcf, Pricer)}")
    print(f"DiscountedCashFlow subclasses Pricer: {issubclass(DiscountedCashFlow, Pricer)}")

    # 2. Polymorphic dispatch through execute_valuation
    spot_quote = 100.0
    val_linear = execute_valuation(linear, spot_quote)
    val_dcf = execute_valuation(dcf, spot_quote)

    print(f"spot price: {spot_quote:.1f}")
    print(f"linear pricer valuation: {val_linear:.2f}")
    print(f"dcf pricer valuation: {val_dcf:.2f}")

    # 3. Encapsulation check
    print(f"linear pricer multiplier attribute: {linear.multiplier:.2f}")
    print(f"linear valuation matches direct calculation: {abs(val_linear - 140.0) < 1e-9}")


main()
LinearPricer conforms to Pricer: True
DiscountedCashFlow conforms to Pricer: True
DiscountedCashFlow subclasses Pricer: True
spot price: 100.0
linear pricer valuation: 140.00
dcf pricer valuation: 95.00
linear pricer multiplier attribute: 1.50
linear valuation matches direct calculation: True

The lab confirms Theorem 1.1: LinearPricer and DiscountedCashFlow both conform to Pricer without any nominal inheritance. The polymorphic valuation function execute_valuation evaluates both models correctly, confirming seamless duck-typed dispatch.

2Where the canon breaks

In traditional object-oriented languages (like Java or C++ prior to concepts), polymorphism strictly requires nominal inheritance from abstract base classes. In quantitative Python systems, forcing all analytics to inherit from a monolithic base class hierarchy causes diamond-inheritance bugs, fragile method resolution order (MRO) resolution, and difficulties mocking objects during testing. Structural protocols decouple interface definition from implementation, allowing third-party classes to satisfy library interfaces without wrapper boilerplate.

3Misconceptions

  1. “A class must inherit from a Protocol class in parentheses to implement its interface.”

    Protocols use structural subtyping. A class implements a Protocol simply by providing the required methods and attributes with compatible signatures. Explicitly subclassing the Protocol is optional and unnecessary.

  2. “Attributes starting with '__' (double underscore) are strictly private and impossible to access from outside the class.”

    Python implements name mangling for attributes with double leading underscores: an attribute __x inside class Filer is renamed to _Filer__x. It remains accessible to any caller who uses the mangled name; Python does not enforce private access control at runtime.

  3. “The @runtime_checkable decorator validates method signatures and argument types at runtime.”

    The @runtime_checkable decorator only verifies that the required attribute names exist and are callable. It does not inspect parameter types, return annotations, or argument counts when isinstance() is called.

4Problem set

Mechanics

M1 · Dunder Str vs. Repr Implementation

Explain the distinct purposes of __repr__ and __str__ for a financial instrument class Bond(cusip, coupon).

Solution

The __repr__ method provides an unambiguous string representation intended for developers and debugging, ideally showing how to reconstruct the object (e.g. Bond(cusip='912828AA0', coupon=0.03)). The __str__ method provides a human-readable representation intended for display to end users. If __str__ is omitted, Python falls back to __repr__.

M2 · Name Mangling Trace

Given class Portfolio: def __init__(self): self.__nav = 1_000_000.0, show how external code can access __nav directly.

Solution

Python's compiler mangles any identifier with two or more leading underscores and at most one trailing underscore by prepending _ClassName. For instance p = Portfolio(), the attribute is accessed as p._Portfolio__nav. Python relies on developer discipline rather than hardware memory protection.

M3 · Defining a Protocol

Write a Protocol definition for a risk metric calculator that requires an evaluate(weights: list[float]) -> float method.

Solution

Using typing.Protocol:

from typing import Protocol, runtime_checkable

@runtime_checkable
class RiskMetric(Protocol):
    def evaluate(self, weights: list[float]) -> float:
        ...

Any class implementing this signature conforms to RiskMetric.

Proof

P1 · Linearization Invariance under C3 Superclass Linearization

Prove that Python's C3 Method Resolution Order (MRO) algorithm guarantees monotonic inheritance: if class \(A\) precedes class \(B\) in the linearization of parent class \(C\), then \(A\) precedes \(B\) in the linearization of any child subclass of \(C\).

Solution

Let \(L(C)\) denote the linearization of class \(C\). The C3 algorithm defines \(L(C) = C + \text{merge}(L(B_1), \dots, L(B_n), B_1 \dots B_n)\) where \(B_i\) are the direct base classes. The merge operation selects a head candidate only if it does not appear in the tail of any other list being merged. By induction on class depth, any ordering \(A \prec B\) established in a parent's linearization is preserved as a constraint in subsequent merges. If a proposed hierarchy violates monotonicity, the merge fails, raising TypeError: Cannot create a consistent method resolution order.

P2 · Runtime Checkable Limitations

Prove that isinstance(obj, Protocol) cannot guarantee type safety when method signatures have incompatible parameter types.

Solution

The implementation of Protocol.__instancecheck__ under @runtime_checkable evaluates hasattr(obj, attr) and verifies that callable attributes are callable via callable(getattr(obj, attr)). It does not perform inspect-based type analysis of parameter annotations during runtime checks. Therefore, if an object defines def price(self, a: str, b: int) -> dict, isinstance returns True even though invoking price(spot: float) raises TypeError. Static checkers (mypy) are required for complete signature verification.

P3 · Instance Attribute Shadowing of Class Attributes

Prove that assigning an attribute on an instance shadows an identical class attribute without mutating the class attribute.

Solution

Attribute lookup on instance obj of class C evaluates obj.__dict__ first (assuming no descriptor overrides). When reading obj.x, if x is in obj.__dict__, that value is returned. Assignment obj.x = v writes directly to obj.__dict__['x'] = v, leaving C.__dict__['x'] untouched. Other instances of C without local bindings continue resolving to the class attribute, proving isolation.

Empirical

E1 · Measuring Attribute Lookup Overhead: __slots__ vs. __dict__

Define a class with standard __dict__ storage and an equivalent class using __slots__ = ('price', 'quantity'), and measure the memory consumption difference.

Solution

Instantiating 100,000 objects reveals that standard instances allocate an internal dictionary consuming approximately 150 bytes per instance. Using __slots__ eliminates the instance dictionary, storing references in a fixed-size C struct array, reducing memory usage to 48 bytes per instance (a 68 percent reduction), which is crucial for managing millions of limit order book entries.

E2 · Method Resolution Order Verification

Construct a diamond inheritance hierarchy and print the resulting __mro__ attribute to verify C3 resolution.

Solution

Defining class A: pass, class B(A): pass, class C(A): pass, and class D(B, C): pass, inspecting D.__mro__ yields (D, B, C, A, object). Python visits \(B\) and its children before visiting \(C\), and visits common base \(A\) only after all derived paths are exhausted.

E3 · Bound vs. Unbound Method Calls

Demonstrate empirically that calling obj.method(x) is functionally and numerically identical to calling Class.method(obj, x).

Solution

Given class P: def val(self, x): return x * 2, calling p = P(); p.val(10) accesses a bound method descriptor that automatically prepends self = p to the argument list. Calling P.val(p, 10) passes p explicitly to the unbound function. Both evaluate to 20 with identical execution results.

Research

R1 · Multiple Inheritance in Trading Frameworks

Evaluate the architectural advantages and maintenance risks of mixin classes versus composition in quantitative execution engines.

Solution

Mixin classes allow injecting reusable capabilities (such as logging or FIX message serialization) across unrelated classes. However, mixins introduce hidden dependencies on instance attributes, obscure initialization order in __init__, and complicate MRO analysis. Object composition (injecting a logger or serializer component via constructor) provides explicit dependencies, easier mocking, and higher architectural stability.

R2 · Abstract Base Classes (ABCs) vs. Structural Protocols

Compare the design tradeoffs between nominal Abstract Base Classes (abc.ABCMeta) and structural protocols (typing.Protocol) in large-scale quantitative software ecosystems.

Solution

ABCs enforce nominal relationships at runtime: subclasses must inherit or register explicitly, enabling shared base implementations. However, ABCs prevent uncoordinated interoperability: third-party models cannot satisfy an ABC without importing the library. Structural protocols decouple interface consumer from producer, enabling seamless static typing and modular interoperability across distributed repositories.

R3 · Garbage Collection and Cyclic References

Explain how cyclic references between orders, fills, and parent portfolios affect CPython's reference counting garbage collector.

Solution

CPython primarily deallocates memory immediately when an object's reference count drops to zero. If an Order references a Portfolio and the Portfolio holds a list of its Order instances, a reference cycle is formed. Even if external variables drop their references, the objects have non-zero reference counts and remain in memory until CPython's generational cyclic garbage collector runs, causing latency spikes and temporary memory bloat.

6Retrieval quiz

  1. What first argument does Python automatically pass to an instance method when called via instance.method()?

    Options

    Instance method invocation binds the instance object as the first parameter (self).

  2. How does a class satisfy a structural Protocol defined using typing.Protocol?

    Options

    Structural protocols rely on structural typing (duck typing); implementing the required interface signatures is sufficient.

  3. What decorator must be applied to a typing.Protocol to allow using isinstance(obj, MyProtocol) at runtime?

    Options

    By default, Protocols can only be used by static type checkers. Applying @runtime_checkable enables dynamic isinstance() checks.

  4. How does Python mangle the name of an attribute defined as __secret inside class Vault?

    Options

    Python prefixes the identifier with an underscore followed by the defining class name.

  5. What does __slots__ achieve when declared on a Python class?

    Options

    __slots__ replaces the dynamic instance dictionary with a compact C struct of pointers, saving memory.

  6. What is the role of __init__ in Python object creation?

    Options

    Memory allocation is handled by __new__, while __init__ receives the newly created instance and initializes its state.

  7. What algorithm does Python use to compute the Method Resolution Order (MRO) for multiple inheritance?

    Options

    Python uses the C3 linearization algorithm to guarantee monotonic order and respect local precedence.

  8. If class Child(ParentA, ParentB) inherits from two independent parents each inheriting from object, how many distinct classes appear between Child and object in Child.__mro__?

    The MRO is (Child, ParentA, ParentB, object), so exactly 2 classes appear between Child and object.
