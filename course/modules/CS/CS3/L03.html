SQL Window Functions

Financial time-series modeling requires rolling statistics: running cumulative returns, moving averages of volatility, drawdown peaks, and peer rankings within trading sectors. Classical SQL aggregation with GROUP BY collapses all rows in a group into a single summary row, destroying underlying event history and requiring expensive self-joins to re-attach original timestamps. Window functions perform calculations across a moving frame of related rows while preserving the complete cardinality and individual identity of every record in the relation.

1Syntax and Framing Mechanics

Building on the relational model and SQL joins, window functions extend relational query engines with ordered partition framing.

Definition 3.1 (SQL Window Function)

A SQL window function is an operator that computes an aggregate or ranking value over a window partition of rows defined by the OVER clause: \[ \text{func}(\text{expr}) \text{ OVER } (\text{PARTITION BY } P \text{ ORDER BY } O \text{ [FRAME]}), \] where:

  • Partitioning (PARTITION BY P): Divides the input relation into disjoint partitions sharing identical values of attributes \(P\). If omitted, the entire table forms a single partition.
  • Ordering (ORDER BY O): Establishes a total or weak ordering of rows within each partition according to expressions \(O\).
  • Window Framing (FRAME): Specifies the sliding subset of rows within the partition evaluated for the current row (e.g. ROWS BETWEEN k PRECEDING AND CURRENT ROW).

Remark 3.1 (ROWS versus RANGE Framing)

The framing clause dictates how peer rows with identical ordering values are treated:

  • ROWS BETWEEN ...: Defines window boundaries by strictly counting physical row offsets relative to the current row index.
  • RANGE BETWEEN ...: Defines window boundaries by logical value offsets relative to the current row's ORDER BY value. Rows with identical ordering values (ties) are grouped together as peers.
In standard SQL, omitting the frame clause when ORDER BY is present defaults to RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW, which aggregates all duplicate peer rows up to the current row.

2Frame Aggregation Equivalence

Window functions provide dramatic computational speedups over correlated self-joins while expressing mathematically equivalent operations.

Theorem 3.1 (Window Frame Self-Join Equivalence)

Let relation \(R\) have unique primary key \((\text{id})\), partition key \(P\), and monotonically increasing sequence index \(S \in \mathbb{Z}\). For any row \(t \in R\), the window aggregate: \[ W(t) = \operatorname{SUM}(V) \text{ OVER } (\text{PARTITION BY } P \text{ ORDER BY } S \text{ ROWS BETWEEN } k \text{ PRECEDING AND CURRENT ROW}) \] is mathematically identical to the correlated self-join aggregate: \[ J(t) = \sum \{s.V : s \in R \land s.P = t.P \land s.S \in [t.S - k, t.S]\}. \]

Proof

Within any partition defined by \(P = p\), let rows be ordered by sequence index \(S\). The frame specification ROWS BETWEEN k PRECEDING AND CURRENT ROW defines the window for tuple \(t\) with index \(S_t\) as the set of rows \(\{s \in R : s.P = t.P\}\) where the index offset satisfies \(0 \le t.S - s.S \le k\). Because sequence index \(S\) is strictly increasing and dense across consecutive integer rows, the condition that \(s\) is between \(k\) preceding rows and the current row is equivalent to the integer interval \(s.S \in [t.S - k, t.S]\). The window operator computes the sum over this set: \(W(t) = \sum_{s \in \operatorname{Frame}(t)} s.V\). The correlated self-join explicitly joins relation \(R\) with itself on \(s.P = t.P \land s.S \in [t.S - k, t.S]\) and computes the grouped sum \(\sum s.V\). Because the sets of joined rows are identical, their sums are equal for all \(t \in R\): \(W(t) \equiv J(t)\).

Example 3.1 (Rolling 3-Day Desk PnL)

Consider daily trading desk records with daily PnL cents. A rolling 3-day window sum uses: 

SELECT desk, day_seq, pnl_cents,
       SUM(pnl_cents) OVER (
           PARTITION BY desk
           ORDER BY day_seq
           ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
       ) AS rolling_3d_pnl
FROM daily_pnl;
For day 3, the window encompasses days 1, 2, and 3 (\(2 \text{ preceding} + \text{current}\)), yielding exactly the sum of PnL across those three days.

Lab 1 · SQL Window Functions and Frame Aggregations

Verifies that the SQLite window function rolling sum over (PARTITION BY desk ORDER BY day_seq ROWS BETWEEN 2 PRECEDING AND CURRENT ROW) matches an independent correlated self-join on all rows.

"""CS3 Lesson 3 Inline Lab 1: SQL window functions and frame aggregations.

Demonstrates rolling window sum using SQLite OVER (PARTITION BY ... ORDER BY ... ROWS BETWEEN).
Verifies the rolling aggregate values against an independent self-join reference.
Data: SIMULATED daily desk PnL records.
"""

from __future__ import annotations

import sqlite3


def main() -> None:
    conn = sqlite3.connect(":memory:")

    with conn:
        conn.execute(
            """
            CREATE TABLE daily_pnl (
                desk TEXT NOT NULL,
                day_seq INT NOT NULL,
                pnl_cents INT NOT NULL
            )
            """
        )

        # SIMULATED PnL data for two desks over 5 days
        pnl_records = [
            ("RATES", 1, 100000),
            ("RATES", 2, -25000),
            ("RATES", 3, 50000),
            ("RATES", 4, 80000),
            ("RATES", 5, -10000),
            ("EQUITY", 1, 40000),
            ("EQUITY", 2, 60000),
            ("EQUITY", 3, -15000),
            ("EQUITY", 4, -30000),
            ("EQUITY", 5, 95000),
        ]
        conn.executemany("INSERT INTO daily_pnl VALUES (?, ?, ?)", pnl_records)

    cur = conn.cursor()

    # 1. Compute rolling 3-day sum using SQL window function
    cur.execute(
        """
        SELECT
            desk,
            day_seq,
            pnl_cents,
            SUM(pnl_cents) OVER (
                PARTITION BY desk
                ORDER BY day_seq
                ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
            ) AS rolling_3d_pnl
        FROM daily_pnl
        ORDER BY desk, day_seq
        """
    )
    window_results = cur.fetchall()

    # 2. Compute rolling 3-day sum using independent self-join reference
    cur.execute(
        """
        SELECT
            a.desk,
            a.day_seq,
            a.pnl_cents,
            SUM(b.pnl_cents) AS ref_rolling_3d_pnl
        FROM daily_pnl a
        JOIN daily_pnl b
          ON a.desk = b.desk
         AND b.day_seq BETWEEN a.day_seq - 2 AND a.day_seq
        GROUP BY a.desk, a.day_seq, a.pnl_cents
        ORDER BY a.desk, a.day_seq
        """
    )
    self_join_results = cur.fetchall()

    print(f"Total evaluated rows: {len(window_results)}")
    all_matched = True
    for w_row, s_row in zip(window_results, self_join_results, strict=True):
        desk, day, pnl, win_sum = w_row
        ref_desk, ref_day, ref_pnl, ref_sum = s_row
        assert desk == ref_desk and day == ref_day and pnl == ref_pnl
        match = win_sum == ref_sum
        if not match:
            all_matched = False
        print(f"Desk {desk} Day {day}: PnL={pnl} -> Rolling 3d Window={win_sum}, Self-join={ref_sum}")

    print(f"Window function matches self-join reference on all rows: {all_matched}")
    conn.close()

3Where the Canon Breaks

Window functions present subtle traps in high-volume quantitative architectures:

  • Silent RANGE Peer Expansion: Writing SUM(vol) OVER (ORDER BY timestamp) without specifying ROWS defaults to RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. If multiple trades share the exact same timestamp millisecond, the window includes all peer rows up to the end of that timestamp group, returning identical inflated sums for all tied rows instead of incremental tick-by-tick progress.
  • Memory Spills on Huge Partitions: While relational databases compute window functions in a single pass over sorted streams, ranking or framing over giant unpartitioned datasets (e.g. 500 million tick trades) requires global external disk sorting, resulting in massive I/O spills.
  • Non-Filterability in WHERE: Window functions evaluate during the SELECT projection phase, strictly after the WHERE, GROUP BY, and HAVING clauses have executed. Writing WHERE ROW_NUMBER() = 1 is a syntax error; filtering on window values requires wrapping the query in a Common Table Expression (CTE) or subquery.

4Misconceptions

  1. A window function collapses input rows like a GROUP BY aggregation.

    Window functions never collapse rows. Every input row in the source relation produces exactly one output row in the result, retaining all original row attributes and timestamps.

  2. ROWS BETWEEN 1 PRECEDING AND CURRENT ROW is identical to RANGE BETWEEN 1 PRECEDING AND CURRENT ROW.

    ROWS specifies an offset of exactly 1 physical row in the ordered partition. RANGE specifies an offset of 1 in value space of the ORDER BY column (for instance, 1 day or 1 second), and aggregates all duplicate peer rows sharing the same value.

  3. You can filter on a window function directly in the WHERE clause of the same query.

    In the SQL logical query processing pipeline, the WHERE clause executes before window functions are calculated. Filtering on a window function requires a subquery or Common Table Expression (CTE).

5Problem Set

Tier 1 · Mechanics

Given daily returns: Day 1: 0.02, Day 2: -0.01, Day 3: 0.03, Day 4: 0.01. Calculate the rolling 2-day sum using ROWS BETWEEN 1 PRECEDING AND CURRENT ROW for Day 1, 2, 3, and 4.

Solution

For Day 1: no preceding row exists, so sum is 0.02. For Day 2: Day 1 + Day 2 = 0.02 + (-0.01) = 0.01. For Day 3: Day 2 + Day 3 = (-0.01) + 0.03 = 0.02. For Day 4: Day 3 + Day 4 = 0.03 + 0.01 = 0.04. Sequence of rolling 2-day sums is: [0.02, 0.01, 0.02, 0.04].

A table contains values [10, 20, 20, 30] ordered ascending. State the output sequences for: (a) ROW_NUMBER(); (b) RANK(); and (c) DENSE_RANK().

Solution

(a) ROW_NUMBER() assigns strictly sequential integers: [1, 2, 3, 4]. (b) RANK() assigns identical ranks to ties and skips subsequent ranks: [1, 2, 2, 4]. (c) DENSE_RANK() assigns identical ranks to ties without skipping: [1, 2, 2, 3].

Explain the difference in result between SUM(pnl) OVER (ORDER BY day) and SUM(pnl) OVER (ORDER BY day ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) when duplicate day values exist.

Solution

The first query defaults to RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. When duplicate day values exist, all peer rows for that day are included in the sum, producing identical total sums for all peer rows. The second query uses ROWS, incrementally adding each physical row one by one.

Tier 2 · Proof

Prove that for any finite ordered partition of size \(N\), the sum of ROW_NUMBER() values across all rows equals \(\frac{N(N+1)}{2}\).

Solution

By Definition 3.1, ROW_NUMBER() assigns a strictly bijective mapping from the ordered partition of size \(N\) to the set of integers \(\{1, 2, \dots, N\}\). The sum across all rows is \(\sum_{i=1}^N i\). By mathematical induction or Gauss's pairing argument, \(\sum_{i=1}^N i = \frac{N(N+1)}{2}\).

Prove that for any ordering, DENSE_RANK() is less than or equal to RANK() for every row in a partition.

Solution

Let rows be ordered \(t_1, \dots, t_N\). For row \(t_i\), RANK() equals \(1 + |\{j < i : t_j.O < t_i.O\}| + |\{j < i : t_j.O = t_i.O\}|\), which is the number of strictly preceding rows plus one. DENSE_RANK() equals \(1 + |\{v \in \operatorname{values}(O) : v < t_i.O\}|\), which counts distinct preceding values. Since the number of distinct values strictly preceding \(t_i.O\) cannot exceed the total number of preceding rows, \(\text{DENSE\_RANK}(t_i) \le \text{RANK}(t_i)\) for all \(i\).

Prove that an incremental sliding window sum over ROWS BETWEEN k PRECEDING AND CURRENT ROW can be computed in \(O(1)\) amortized time per row using a running accumulator.

Solution

Let \(S_i = \sum_{j=i-k}^i x_j\) denote the window sum at row \(i\). At step \(i+1\), the new window sum is \(S_{i+1} = \sum_{j=i+1-k}^{i+1} x_j = S_i + x_{i+1} - x_{i-k}\). This recurrence requires exactly one addition and one subtraction per row. Maintaining a circular buffer or pointer of length \(k\) allows retrieving the departing value \(x_{i-k}\) in \(O(1)\) time. Thus, each transition executes in \(O(1)\) time, bounding total runtime for \(N\) rows to \(O(N)\).

Tier 3 · Empirical

A trading firm queries a 20-day rolling moving average of prices over 10 million trade records. A naive implementation uses a self-join requiring \(10^7 \times 20 = 2 \times 10^8\) row evaluations. The database window function executes in a single streaming pass touching 10 million rows. Calculate the computational speedup factor.

Solution

The self-join approach touches \(2 \times 10^8\) rows across its join evaluation, whereas the streaming window function with accumulator touches each row exactly once (\(10^7\) row evaluations). The computational speedup factor is \((2 \times 10^8) / 10^7 = 20.0\)x, directly proportional to the window width.

A portfolio manager computes maximum drawdown by comparing current portfolio value \(V_t\) to the cumulative maximum \(\max_{s \le t} V_s\). Write the SQL window expression for cumulative peak value and calculate the peak value at Day 4 for values: Day 1: 100, Day 2: 105, Day 3: 102, Day 4: 98.

Solution

The SQL window expression is: MAX(value) OVER (ORDER BY day ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW). Evaluating through time: Day 1 peak = 100; Day 2 peak = \(\max(100, 105) = 105\); Day 3 peak = \(\max(105, 102) = 105\); Day 4 peak = \(\max(105, 98) = 105\). The peak value at Day 4 is 105.

An equity cross-sectional strategy ranks 3,000 stocks daily by momentum score using DENSE_RANK() OVER (PARTITION BY date ORDER BY momentum_score DESC). If 50 stocks tie for rank 1, what rank is assigned to the next best performing stock?

Solution

Because DENSE_RANK() does not skip rank integers following duplicate ties, all 50 tied top-performing stocks receive rank 1, and the next best performing stock receives rank 2. (If RANK() had been used instead, the next stock would have received rank 51).

Tier 4 · Research

Analyze the algorithmic complexity difference between offline relational window evaluation (requiring full sort) and online streaming window evaluation using monotonic deques for rolling min/max.

Solution

In offline relational engines, evaluating window functions requires a sort step on the partition and order keys taking \(O(N \log N)\) time and \(O(N)\) memory. In online event streaming (e.g., streaming algorithmic market feeds), sorting is impossible. Rolling min/max can be maintained in \(O(1)\) amortized time per incoming tick using a double-ended queue (monotonic deque) that stores index-value pairs in monotonic order, dropping dominated elements.

Evaluate how window frame boundaries must be defined to prevent look-ahead bias when computing rolling realized volatility for intraday signal generation.

Solution

In signal generation, an indicator computed at time \(t\) must depend strictly on information available at or before \(t\). The window frame must be explicitly bounded on the right by CURRENT ROW or 1 PRECEDING (e.g., ROWS BETWEEN k PRECEDING AND CURRENT ROW). Centered window frames such as ROWS BETWEEN k PRECEDING AND k FOLLOWING incorporate future observations \(t+1, \dots, t+k\), creating fatal look-ahead bias that invalidates historical backtest realism.

Discuss why traditional relational query optimizers struggle to parallelize window functions across distributed nodes when queries lack a PARTITION BY clause.

Solution

When a query contains PARTITION BY P, independent partition keys can be hashed and routed to distinct worker nodes to evaluate windows in parallel with zero inter-node communication. When PARTITION BY is omitted, the ordering is global. All worker data must shuffle to a single coordinator node to construct the global total order, creating a severe network bandwidth bottleneck and eliminating horizontal scaling benefits.

7Retrieval quiz

  1. How does a SQL window function differ from a GROUP BY aggregation in terms of output row count?

    Options

    Window functions compute aggregated values over a frame while retaining every individual row in the relation.

  2. What does the clause ROWS BETWEEN 2 PRECEDING AND CURRENT ROW specify?

    Options

    ROWS specifies physical row offsets, so 2 preceding plus current equals 3 rows.

  3. Which ranking function produces gapless rank numbers when duplicate ordering values exist?

    Options

    DENSE_RANK() assigns identical ranks to ties without skipping subsequent integers.

  4. In a table with values [100, 200, 200, 300], what is the DENSE_RANK() value for 300?

    Distinct values are 100 (rank 1), 200 (rank 2), and 300 (rank 3).

  5. What is the default framing clause when ORDER BY is provided in an OVER clause without an explicit frame?

    Options

    Standard SQL defaults to RANGE from UNBOUNDED PRECEDING to CURRENT ROW when ORDER BY is specified.

  6. Why can you not filter directly on a window function in the WHERE clause?

    Options

    In the logical query evaluation model, WHERE filters rows before the SELECT list (where window functions are computed) is executed.

  7. Which navigation function returns the attribute value from the previous row in the ordered partition?

    Options

    LAG() accesses data from a preceding row at a specified physical offset without a self-join.

  8. What computational complexity does an incremental sliding window sum achieve per row using an accumulator?

    Options

    An accumulator adds the entering element and subtracts the departing element in constant O(1) time.
