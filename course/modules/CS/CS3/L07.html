Columnar Storage and Parquet

Quantitative analytical workloads are column-intensive. Calculating an average price, estimating a covariance matrix, or evaluating factor exposures scans millions of rows across only two or three columns out of a fifty-column table. Traditional row-oriented databases force the operating system to load every unneeded attribute into CPU cache, bottlenecking queries on I/O bandwidth. Columnar storage fundamentally reorders physical memory layout by storing contiguous vectors of homogeneous column data. Coupled with vectorized execution engines like DuckDB and compressed disk formats like Apache Parquet, columnar storage reduces physical I/O transfer by over eighty percent.

1Row-Oriented vs Columnar Architecture

Building on physical storage concepts from database indexes, columnar systems redefine memory organization.

Definition 7.1 (Columnar Storage)

Columnar storage (Decomposition Storage Model, DSM) stores all values of each column contiguously in memory and on disk, contrasting with row-oriented storage (N-ary Storage Model, NSM) where all attributes of a single tuple reside contiguously on a page. In a table of \(N\) rows and \(M\) columns, row storage stores values in sequence \((c_{1,1}, \dots, c_{1,M}), (c_{2,1}, \dots, c_{2,M}), \dots\), whereas columnar storage stores vectors \((c_{1,1}, \dots, c_{N,1}), \dots, (c_{1,M}, \dots, c_{N,M})\).

Definition 7.2 (Parquet Format)

The Parquet format is an open-source, columnar binary file format structured hierarchically:

  1. Row Groups: Horizontal partitions of rows (typically 100,000 to 1,000,000 rows each) enabling parallel reading.
  2. Column Chunks: Contiguous byte streams within each row group holding data for a single column.
  3. Data Pages: Indivisible units of compression and encoding (typically 1 MiB) within a column chunk.
  4. File Footer: Trailing metadata containing the full schema, page locations, and statistics (min/max/null counts) per chunk for predicate pushdown.

Remark 7.1 (DuckDB and Vectorized Execution)

DuckDB is an embeddable analytical database running in-process without client-server socket overhead. DuckDB combines columnar storage with vectorized query execution, processing columnar arrays in fixed-size vector chunks (typically 2048 values) that fit directly within CPU L1/L2 caches, eliminating per-tuple interpretation dispatch.

2Projection Pruning and Compression

The mathematical performance advantage of columnar architecture over row stores derives from projection pruning.

Theorem 7.1 (Projection Pruning I/O Reduction Invariant)

Let a relation \(R\) have \(M\) columns with byte widths \(w_1, w_2, \dots, w_M\), such that total row width is \(W_{\text{row}} = \sum_{i=1}^M w_i\). For an analytical aggregation referencing attribute subset \(Q \subseteq \{1, \dots, M\}\), the theoretical physical bytes scanned under columnar layout \(B_{\text{col}}\) versus row layout \(B_{\text{row}}\) for \(N\) uncompressed rows satisfies: \[ \frac{B_{\text{col}}}{B_{\text{row}}} = \frac{\sum_{j \in Q} w_j}{\sum_{i=1}^M w_i} < 1 \quad (\text{for all } Q \subsetneq \{1, \dots, M\}). \] The I/O bandwidth reduction factor is given by \(\rho = W_{\text{row}} / \sum_{j \in Q} w_j\).

Proof

In a row-oriented storage model, entire row tuples are serialized contiguously across disk pages. To evaluate any predicate or aggregation on attribute subset \(Q\), the storage subsystem must transfer entire page blocks into memory buffers, reading all \(W_{\text{row}}\) bytes per row: \(B_{\text{row}} = N \times W_{\text{row}} = N \sum_{i=1}^M w_i\). In a columnar storage model, each column vector is stored in separate contiguous blocks. The query planner identifies that only columns \(j \in Q\) are required (projection pruning). The storage engine issues read requests strictly for the column chunks corresponding to \(Q\), reading \(B_{\text{col}} = N \sum_{j \in Q} w_j\). Dividing \(B_{\text{col}}\) by \(B_{\text{row}}\) yields the ratio \(\sum_{j \in Q} w_j / \sum_{i=1}^M w_i\). Since all column widths \(w_i > 0\) and \(Q\) is a proper subset of all columns, this ratio is strictly less than 1, proving the invariant.

Example 7.1 (Market Trade Price Aggregation)

Suppose a trade table contains 8 fields: trade_id (8B), timestamp (8B), price (8B), qty (4B), venue (4B), trader (4B), account (4B), and flags (4B), totaling \(W_{\text{row}} = 44\) bytes. Evaluating SELECT AVG(price) FROM trades requires only the 8-byte price column. The I/O ratio is \(8 / 44 \approx 0.1818\), achieving an exact 5.50x I/O reduction factor and pruning 81.8% of memory bus traffic.

Lab 1 · Columnar Storage vs Row Layout Projection Pruning

Verifies that evaluating an average price query over 10,000 simulated trade records reads exactly 440,000 bytes in a row store versus 80,000 bytes in a columnar store, achieving an exact 5.50x bandwidth reduction factor.

"""CS3 Lesson 7 Inline Lab 1: Columnar storage vs row layout projection pruning.

Measures memory buffers and bytes scanned for a single-column analytical aggregation
under row-oriented (NSM) versus columnar (DSM) physical layouts.
Data: SIMULATED trade records.
"""

from __future__ import annotations

import struct
from typing import NamedTuple


class RowTrade(NamedTuple):
    trade_id: int  # int64 (8 bytes)
    timestamp_ns: int  # int64 (8 bytes)
    price_cents: int  # int64 (8 bytes)
    qty: int  # int32 (4 bytes)
    venue_id: int  # int32 (4 bytes)
    trader_id: int  # int32 (4 bytes)
    account_id: int  # int32 (4 bytes)
    flags: int  # int32 (4 bytes)
    # Total row size: 8 + 8 + 8 + 4 + 4 + 4 + 4 + 4 = 44 bytes


ROW_FORMAT = "=qqqiiiii"
ROW_SIZE = struct.calcsize(ROW_FORMAT)  # 44 bytes


def simulate_row_store(n_rows: int) -> bytes:
    """Serialize n_rows into a contiguous row-major binary buffer."""
    buf = bytearray()
    for i in range(n_rows):
        packed = struct.pack(
            ROW_FORMAT,
            100000 + i,  # trade_id
            1600000000000000000 + i * 1000,  # timestamp_ns
            15025 + (i % 50),  # price_cents
            100 + (i % 10) * 10,  # qty
            1,  # venue_id
            42,  # trader_id
            999,  # account_id
            0,  # flags
        )
        buf.extend(packed)
    return bytes(buf)


def simulate_column_store(n_rows: int) -> dict[str, bytes]:
    """Serialize n_rows into individual column vectors."""
    trade_ids = bytearray()
    timestamps = bytearray()
    prices = bytearray()
    qtys = bytearray()
    venues = bytearray()
    traders = bytearray()
    accounts = bytearray()
    flags = bytearray()

    for i in range(n_rows):
        trade_ids.extend(struct.pack("=q", 100000 + i))
        timestamps.extend(struct.pack("=q", 1600000000000000000 + i * 1000))
        prices.extend(struct.pack("=q", 15025 + (i % 50)))
        qtys.extend(struct.pack("=i", 100 + (i % 10) * 10))
        venues.extend(struct.pack("=i", 1))
        traders.extend(struct.pack("=i", 42))
        accounts.extend(struct.pack("=i", 999))
        flags.extend(struct.pack("=i", 0))

    return {
        "trade_id": bytes(trade_ids),
        "timestamp_ns": bytes(timestamps),
        "price_cents": bytes(prices),
        "qty": bytes(qtys),
        "venue_id": bytes(venues),
        "trader_id": bytes(traders),
        "account_id": bytes(accounts),
        "flags": bytes(flags),
    }


def main() -> None:
    n_rows = 10000
    row_buffer = simulate_row_store(n_rows)
    column_store = simulate_column_store(n_rows)

    print(f"Total simulated rows: {n_rows}")
    print(f"Row layout record size: {ROW_SIZE} bytes")
    print(f"Total row buffer size: {len(row_buffer)} bytes ({len(row_buffer) / 1024:.1f} KiB)")

    # Analytical query: SELECT AVG(price_cents) FROM trades
    # 1. In row-store: must stream all records; each price requires stride through row buffer
    row_bytes_read = len(row_buffer)  # I/O subsystem must scan entire row blocks
    price_sum_row = 0
    for i in range(n_rows):
        offset = i * ROW_SIZE
        # price_cents is 3rd field: offset + 8 (trade_id) + 8 (timestamp_ns) = offset + 16
        price_cents = struct.unpack_from("=q", row_buffer, offset + 16)[0]
        price_sum_row += price_cents
    avg_price_row = price_sum_row / n_rows

    # 2. In column-store: projection pruning reads ONLY the price_cents vector
    price_vector = column_store["price_cents"]
    column_bytes_read = len(price_vector)
    price_sum_col = 0
    for i in range(n_rows):
        price_cents = struct.unpack_from("=q", price_vector, i * 8)[0]
        price_sum_col += price_cents
    avg_price_col = price_sum_col / n_rows

    assert avg_price_row == avg_price_col

    print(f"Calculated average price: {avg_price_row:.2f} cents")
    print(f"Row store bytes scanned: {row_bytes_read} bytes")
    print(f"Column store bytes scanned: {column_bytes_read} bytes")
    print(f"I/O Reduction Factor: {row_bytes_read / column_bytes_read:.2f}x")
    print(f"Exact theoretical savings: {(1.0 - column_bytes_read / row_bytes_read) * 100:.1f}% bandwidth pruned")
    assert column_bytes_read == n_rows * 8
    assert row_bytes_read == n_rows * 44


main()
Total simulated rows: 10000
Row layout record size: 44 bytes
Total row buffer size: 440000 bytes (429.7 KiB)
Calculated average price: 15049.50 cents
Row store bytes scanned: 440000 bytes
Column store bytes scanned: 80000 bytes
I/O Reduction Factor: 5.50x
Exact theoretical savings: 81.8% bandwidth pruned

The benchmark confirms that columnar projection pruning eliminates 81.8% of data transfers while reproducing the exact identical aggregated average price.

3Where the Canon Breaks

Columnar storage introduces fundamental trade-offs that make it unsuitable for transactional workloads:

  • Prohibitive Single-Row Insert Latency: In an OLTP row store, inserting a new trade appends one 44-byte block to the end of the active page. In a columnar store, appending a single row requires seeking and writing to \(M\) distinct column files or chunks, multiplying disk head movements and transaction commit latency by \(M\). Columnar engines require batch ingestion buffers.
  • Dictionary Page Overflow on Floats: Columnar engines achieve high compression using dictionary encoding on repetitive strings or integers. Real-world financial floating-point prices and fractional interest rates have high entropy with near-unique trailing digits, causing dictionary tables to overflow and reverting to raw bit storage without compression gains.
  • Update and Delete Penalties: Updating a single cell in a Parquet file cannot be done in place without decompressing and rewriting the entire row group. Analytical columnar engines require copy-on-write delta files or merge-on-read architectures.

4Misconceptions

  1. Columnar databases are always faster than row databases for all queries.

    Columnar databases are superior for analytical scans across many rows and few columns (OLAP). For point queries selecting an entire row by primary key (SELECT * WHERE id = 123), columnar stores must reconstruct the tuple from \(M\) separate column vectors, performing significantly worse than a row store.

  2. Parquet files require an external database server to be read.

    Parquet is a self-contained, serverless binary file format. All schema, column chunks, data pages, and statistics are stored inside the file itself. In-process engines like DuckDB or embedded Python readers parse Parquet files directly from local disk or cloud object storage without any active daemon.

  3. Compressing columns with gzip or snappy is all that columnar formats do.

    Generic byte compressors (gzip, snappy) operate on raw byte streams. Columnar engines apply lightweight column-aware encodings (dictionary encoding, run-length encoding, delta encoding, bit-packing) that allow database execution engines to evaluate filter predicates directly on encoded vectors without decompressing.

5Problem Set

Tier 1 · Mechanics

A historical trade table has 30 columns totaling 120 bytes per row. An algorithm scans 100,000,000 rows to calculate the sum of trading volume (a single 8-byte column). Calculate the total gigabytes transferred under: (a) a row store; and (b) a columnar store.

Solution

(a) In a row store: \(100 \times 10^6 \times 120 \text{ bytes} = 1.2 \times 10^{10} \text{ bytes} = 12.0 \text{ GB}\). (b) In a columnar store: \(100 \times 10^6 \times 8 \text{ bytes} = 8.0 \times 10^8 \text{ bytes} = 0.8 \text{ GB}\) (800 MB). Columnar projection pruning reduces I/O transfer by 11.2 GB (a 15x reduction factor).

Explain how a Parquet file's footer statistics (min and max values per column chunk) enable predicate pushdown for a query: WHERE trade_date = '2020-05-15'.

Solution

The reader inspects the footer metadata before loading any data pages. For each row group, it checks whether the query target ('2020-05-15') falls within the recorded \([\min(\text{trade\_date}), \max(\text{trade\_date})]\) interval. If the target date is strictly less than min or greater than max, the query engine skips the entire row group, avoiding reading any compressed data pages from disk.

A column of 1,000,000 trade venue strings contains only three distinct values: 'NASDAQ', 'NYSE', and 'BATS'. Calculate the uncompressed byte size versus a 2-bit dictionary-encoded bit-packed vector.

Solution

Uncompressed strings averaging 5 bytes require \(1{,}000{,}000 \times 5 = 5{,}000{,}000\) bytes (5.0 MB). With dictionary encoding, 3 distinct values require \(\lceil \log_2 3 \rceil = 2\) bits per row. Total bit-packed storage is \(1{,}000{,}000 \times 2 \text{ bits} = 2{,}000{,}000 \text{ bits} = 250{,}000\) bytes (250 KB), plus negligible dictionary table overhead. Dictionary encoding achieves a 20x compression ratio.

Tier 2 · Proof

Prove that run-length encoding (RLE) on a sorted column with \(U\) distinct contiguous runs achieves a compression ratio bounded by \(O(N / U)\).

Solution

In an uncompressed column of \(N\) elements of size \(w\) bytes, total size is \(S_{\text{raw}} = N \cdot w\). Run-length encoding stores each contiguous run as a pair \((\text{value}, \text{count})\), requiring \(w + w_{\text{count}}\) bytes per run. For \(U\) distinct runs, total encoded size is \(S_{\text{RLE}} = U (w + w_{\text{count}})\). The compression ratio is \(S_{\text{raw}} / S_{\text{RLE}} = (N \cdot w) / [U (w + w_{\text{count}})] = \frac{w}{w + w_{\text{count}}} \cdot \frac{N}{U} = O(N / U)\). For highly repetitive data where \(U \ll N\), RLE achieves massive linear compression proportional to average run length \(N/U\).

Prove that tuple reconstruction cost for \(M\) columns under columnar storage requires \(M\) distinct memory gathers, and establish the conditions under which row stores outperform column stores.

Solution

In a columnar store, each column vector \(C_j\) is stored in a separate memory buffer. To materialize a complete row tuple \(t_i = (C_1[i], \dots, C_M[i])\), the CPU must issue \(M\) distinct memory read operations at non-contiguous memory offsets \(C_j + i \cdot w_j\). In a row store, the tuple resides contiguously at offset \(i \cdot W_{\text{row}}\), loading all \(M\) attributes in 1 memory fetch (or 1 cache line). If a query projects \(k\) columns, columnar requires \(k\) memory gathers. When \(k / M\) approaches 1 and the query selects few rows (point lookups), the cache-locality penalty of \(M\) scattered gathers exceeds the sequential row fetch cost, proving that row stores outperform column stores for full-tuple point lookups.

Prove that delta encoding on monotonically increasing integer timestamps converts unbounded dynamic range into a bounded difference domain.

Solution

Let raw timestamps be strictly increasing: \(T_0 < T_1 < \dots < T_N\). In raw representation, each timestamp requires 64 bits to span historical epochs (\(0 \le T_i < 2^{64}\)). Delta encoding stores the initial anchor \(T_0\) and consecutive forward differences \(\Delta_i = T_i - T_{i-1} > 0\). If maximum sampling interval is bounded by \(\Delta_{\max}\), then \(\Delta_i \in [1, \Delta_{\max}]\). Each delta can be packed in \(\lceil \log_2(\Delta_{\max}) \rceil\) bits. For tick data sampled at microsecond intervals with \(\Delta_{\max} \le 1000\), each timestamp is compressed from 64 bits down to 10 bits, proving domain boundedness.

Tier 3 · Empirical

A quantitative firm migrates a 5-terabyte CSV tick dataset to compressed Apache Parquet with Snappy compression. If Parquet reduces physical disk footprint to 600 gigabytes, calculate the compression ratio and quantify the monthly cloud object storage cost reduction at \$0.023 per GB/month.

Solution

Initial storage is 5,000 GB, and compressed Parquet storage is 600 GB. The compression ratio is \(5000 / 600 \approx 8.33\)x (an 88.0% space reduction). Initial monthly storage cost is \(5000 \times \$0.023 = \$115.00\). New storage cost is \(600 \times \$0.023 = \$13.80\). Monthly cost reduction is \(\$115.00 - \$13.80 = \$101.20\) per month (88% cost savings).

An analytical query in DuckDB computes SUM(volume) across 50 million trades stored in Parquet. The file is split into 50 row groups of 1 million rows each. Predicate pushdown on trade_date eliminates 45 of the 50 row groups. Calculate the percentage of data pages skipped without reading from disk.

Solution

Total row groups is 50. The query optimizer skips 45 row groups using footer min/max statistics. The percentage of skipped data is \(45 / 50 = 0.90\) or 90.0%. Only 5 row groups (10% of the dataset) are decompressed and scanned into memory.

A portfolio backtesting script reads equity prices using Python csv.reader versus vectorized DuckDB querying the equivalent Parquet table. The CSV scan takes 45.0 seconds, while DuckDB completes in 0.9 seconds. Calculate the execution speedup factor.

Solution

Execution time drops from 45.0 seconds to 0.9 seconds. The speedup factor is \(45.0 / 0.9 = 50.0\)x. Vectorized C++ columnar decoding, multithreaded decompression, and SIMD projection eliminate Python string parsing overhead.

Tier 4 · Research

Analyze why in-process embeddable analytical databases (such as DuckDB) eliminate the primary performance bottlenecks of client-server database architectures (such as PostgreSQL) for data science workloads.

Solution

Client-server databases communicate over TCP loopback sockets or Unix domain sockets. To transfer 10 million rows to a Python process, PostgreSQL must serialize records into network wire protocol packets, incur OS kernel context switches, send data through socket buffers, and deserialize objects in Python memory. DuckDB runs embedded in the Python process memory space. Query results are written directly into Apache Arrow memory pointers shared with NumPy and pandas with zero socket overhead, zero serialization, and zero memory copying.

Evaluate the architectural trade-offs between Apache Arrow (in-memory columnar specification) and Apache Parquet (on-disk storage format) in modern quantitative pipelines.

Solution

Apache Parquet is optimized for cold on-disk storage: it uses heavy compression (snappy, zstd), complex variable-length bit-packing, and deep hierarchical row groups that must be decoded before CPU processing. Apache Arrow is an uncompressed (or lightly compressed) in-memory columnar format optimized for SIMD vector execution and zero-copy sharing across programming languages (C++, Python, Rust). A production quant pipeline stores historical data in Parquet on disk and memory-maps or decodes it into Arrow tables in RAM for model training.

How does column chunk dictionary encoding enable filter evaluation directly on compressed data vectors without decompressing underlying string payloads?

Solution

When a column chunk is dictionary-encoded, string values are replaced by small integer IDs (e.g., 0, 1, 2) and an auxiliary dictionary table maps IDs to string values. To evaluate WHERE symbol = 'AAPL', the query engine looks up 'AAPL' once in the dictionary table, finding ID = 1. It then executes a vectorized equality scan directly on the array of integer IDs (id == 1) using hardware vector instructions. Because integer comparison is orders of magnitude faster than string comparison and strings never need decoding, query throughput increases dramatically.

7Retrieval quiz

  1. What is the physical storage layout difference between row stores (NSM) and columnar stores (DSM)?

    Options

    Row stores serialize full tuples contiguously; columnar stores serialize each column vector contiguously.

  2. What is projection pruning in columnar databases?

    Options

    Projection pruning avoids reading column chunks from disk when those columns are not needed by the query.

  3. Where does a Parquet file store the schema and column chunk min/max statistics?

    Options

    Parquet stores file metadata and chunk statistics in the file footer so readers can seek directly to metadata first.

  4. If a table has total row width of 50 bytes and an analytical query references 10 bytes of columns, what percentage of I/O transfer is pruned?

    Queried ratio is 10/50 = 20%. Pruned percentage is 100% - 20% = 80%.

  5. Why do columnar stores compress data much more effectively than row stores?

    Options

    Homogeneous data vectors exhibit high redundancy, enabling specialized encodings like RLE, delta, and dictionary compression.

  6. What query workload is poorly suited for a columnar database?

    Options

    Inserting or updating single rows requires modifying multiple separate column chunks, creating high write latency.

  7. What is the role of Apache Arrow in modern data engineering?

    Options

    Arrow provides an in-memory columnar layout for fast SIMD processing and zero-copy data sharing between languages.

  8. How does DuckDB execute queries differently from traditional row-at-a-time iterators?

    Options

    DuckDB uses vectorized execution vectors (e.g. 2048 values) to maximize CPU cache locality and instruction pipelining.
