Database Indexes

High-frequency trading environments and multi-asset risk engines query billions of records daily. Without indexing, answering a point lookup or date-range query forces the database engine to perform a full table scan, reading every disk page into memory and exhausting storage bandwidth. Database indexes provide accelerated physical access paths, transforming linear \(O(N)\) scans into logarithmic \(O(\log N)\) lookups. However, indexes are not free: every secondary index imposes severe write amplification on data ingestion, creating a fundamental architectural trade-off between query speed and write throughput.

1Physical Access Paths and Index Types

Building on the logical relational model, database indexes bridge declarative queries with physical hardware storage layout.

Definition 6.1 (Database Index and Structural Variants)

A database index is an auxiliary physical data structure that maps search key values to storage row locations to accelerate data retrieval. Core index variants include:

  1. B-Tree Index: A balanced multi-way search tree with high fanout \(B\), maintaining sorted key order across leaf pages linked in physical sequence.
  2. Clustered (Primary) Index: An index that dictates the actual physical order of data rows on disk storage pages. A table can have at most one clustered index.
  3. Secondary (Non-Clustered) Index: An auxiliary structure whose leaf nodes store search keys alongside row identifiers (pointers or clustered key values) that point into the primary table heap.
  4. Covering Index: An index containing all columns requested by a query (both predicate columns and projected attributes), allowing the engine to satisfy the query entirely from index pages without accessing the table heap.

Remark 6.1 (Write Amplification)

While indexes accelerate reads, they impose write amplification. When a new row is appended to a table with \(M\) secondary indexes, the database engine must execute 1 heap write plus \(M\) distinct B-tree insert operations, each potentially triggering node splits, leaf rebalancing, and dirty page writebacks to storage.

2Search Complexity Bounds

The performance superiority of database indexing over full table scans is governed by logarithmic tree depth.

Theorem 6.1 (B-Tree Search Complexity Bound)

Let a table contain \(N\) records stored in a B-tree index of fanout (order) \(B \ge 2\). The maximum number of page I/O transfers required to locate any target key is bounded by: \[ H \le \left\lceil \log_{\lceil B / 2 \rceil} \left( \frac{N + 1}{2} \right) \right\rceil + 1 = O\left(\frac{\log N}{\log B}\right), \] compared to an unindexed sequential scan requiring \(\Theta(N)\) record inspections and \(\Theta(N / P)\) page I/O reads (where \(P\) is the page record capacity).

Proof

In a valid B-tree of order \(B\), every internal node except the root has at least \(\lceil B / 2 \rceil\) child pointers. At depth 0 (the root), there is at least 1 node. At depth 1, there are at least 2 nodes. At depth \(h\), there are at least \(2 \lceil B / 2 \rceil^{h-1}\) nodes. Each leaf node holds at least \(\lceil B / 2 \rceil - 1\) keys. Therefore, the minimum total number of keys \(N\) stored in a tree of height \(h\) satisfies: \[ N \ge 1 + 2 (\lceil B / 2 \rceil - 1) \sum_{i=1}^{h-1} \lceil B / 2 \rceil^{i-1} = 1 + 2 (\lceil B / 2 \rceil^{h-1} - 1) = 2 \lceil B / 2 \rceil^{h-1} - 1. \] Rearranging for height \(h\): \[ \frac{N + 1}{2} \ge \lceil B / 2 \rceil^{h-1} \implies h - 1 \le \log_{\lceil B / 2 \rceil} \left( \frac{N + 1}{2} \right) \implies h \le \left\lceil \log_{\lceil B / 2 \rceil} \left( \frac{N + 1}{2} \right) \right\rceil + 1. \] Because searching traverses from root to leaf, it touches exactly \(h\) nodes. For large fanout \(B\) (e.g. \(B \approx 500\) for 4 KiB disk pages), height \(h \le 3\) even for millions of records, yielding \(O(\log_B N)\) page reads.

Example 6.1 (Covering Index for Point-in-Time Queries)

In the Atlas A2 data layer, observation lookups execute: 

SELECT value FROM observations
WHERE source = ? AND series = ? AND retrieved <= ? AND date <= ?
ORDER BY date DESC, seq DESC LIMIT 1;
A composite index on (source, series, retrieved, date, seq, value) is a covering index. The database locates the matching leaf page in \(O(\log N)\) page reads and retrieves value directly from the index key entry without touching the observations table heap.

3Where the Canon Breaks

Physical database indexing exhibits notable performance traps under quantitative workloads:

  • UUID Index Fragmentation: Creating a primary B-tree index on randomly generated UUID strings destroys spatial locality. Because UUID hashes scatter uniformly, every insertion targets a random disk page, causing 50% average page fill factor, massive index page splits, and excessive I/O thrashing. Financial stores require sequential, time-ordered primary keys (e.g. timestamp + autoincrement sequence).
  • Index Scans Slower than Full Scans on High Selectivity: If a query predicate matches 40% of the table rows, scanning through a secondary non-clustered index forces random disk I/O to dereference heap pointers for 40% of records. Query optimizers correctly abandon the index and perform a sequential table scan because sequential I/O is 10x to 50x faster than random I/O on rotating magnetic disks and block SSDs.
  • Ingestion Stalls on High-Frequency Feeds: Appending 100,000 ticks per second into an unindexed table is an append-only sequential stream. Adding three secondary indexes forces 300,000 random B-tree leaf modifications per second, causing transaction lock contention and ingestion buffer overflows. High-frequency tick engines ingest into unindexed memory buffers and build indexes during end-of-day batch processing.

4Misconceptions

  1. Adding more indexes always improves database query performance.

    Every index consumes storage space and incurs write amplification during INSERT, UPDATE, and DELETE operations. Furthermore, having too many redundant indexes confuses query optimizers and bloats database buffer pool memory.

  2. A table can have multiple clustered indexes.

    A clustered index defines the actual physical storage order of the rows on disk pages. Because data rows can physically reside in only one physical sequence, a table can have at most one clustered index.

  3. An index on (A, B) is equally fast for queries filtering only on B.

    B-trees are sorted lexicographically by the leftmost index prefix. An index on (A, B) is sorted primarily by A, and only secondarily by B within identical values of A. A query filtering strictly on B cannot perform an index range seek and must scan the entire index.

5Problem Set

Tier 1 · Mechanics

A B-tree index of order \(B = 100\) holds 1,000,000 records. Calculate the maximum theoretical height of the tree and the maximum number of disk page reads required to locate any single record.

Solution

Minimum node fanout is \(\lceil B / 2 \rceil = 50\). The maximum height satisfies \(h \le \lceil \log_{50}((10^6 + 1)/2) \rceil + 1 = \lceil \log_{50}(500{,}000) \rceil + 1\). Since \(50^3 = 125{,}000\) and \(50^4 = 6{,}250{,}000\), \(\log_{50}(500{,}000) \approx 3.35\), so \(\lceil 3.35 \rceil = 4\). Maximum height is \(4 + 1 = 5\). In practice with standard fill factors, at most 4 page I/O reads are needed.

A composite index is created on (ticker, trade_date, trade_time). Which of the following query predicates can use an index seek: (a) WHERE ticker = 'AAPL'; (b) WHERE trade_date = '2020-01-02'; (c) WHERE ticker = 'AAPL' AND trade_date = '2020-01-02'?

Solution

(a) Can use index seek because ticker is the leading leftmost prefix. (b) Cannot use index seek because the leading attribute ticker is missing (requires an index scan). (c) Can use index seek because both ticker and trade_date form a contiguous leftmost prefix of the composite index.

In a table of 10,000,000 trade records stored in 4 KiB pages holding 50 rows each (200,000 pages), how many page reads does a full table scan require versus an indexed point lookup taking 3 page reads?

Solution

A full table scan must read all 200,000 heap pages into memory. An indexed point lookup traverses 3 B-tree index pages plus 1 heap page (4 page reads total). The index reduces I/O from 200,000 pages to 4 pages, achieving a 50,000x I/O reduction factor.

Tier 2 · Proof

Prove that for an unindexed table of \(N\) records stored in random order, any deterministic algorithm requires \(\Omega(N)\) comparisons in the worst case to determine that a target key is absent.

Solution

An adversary can place the search target at the last uninspected position or omit it entirely. Let an algorithm inspect \(k < N\) records. There remain \(N - k \ge 1\) uninspected records. The adversary can set one of the remaining records to the target key without contradicting any prior inspection. Therefore, the algorithm cannot conclude that the key is absent without inspecting all \(N\) positions. Hence, the adversary forces \(N\) comparisons, establishing an \(\Omega(N)\) lower bound.

Prove that a covering index eliminates all heap table page reads for a query projecting subset \(A \subseteq \operatorname{attr}(\text{Index})\).

Solution

In a non-covering secondary index, leaf nodes store search key values alongside tuple identifiers (TIDs) or primary key values pointing to the table heap. The query engine must execute a secondary heap read for each qualifying index entry to retrieve attributes not stored in the index. When all projected and filtered attributes belong to the index schema \(A \subseteq \operatorname{attr}(\text{Index})\), all required values are present in the index leaf pages. Because no attribute needs to be fetched from the heap, the engine executes an index-only scan, requiring exactly zero heap page accesses.

Prove that if a secondary index has fanout \(B\) and storage fill factor \(\alpha \in (0, 1]\), the effective fanout is \(\alpha B\), and the tree height grows inversely with \(\log(\alpha B)\).

Solution

If each node of capacity \(B\) has fill factor \(\alpha\), the average number of children per internal node is \(B_{\text{eff}} = \alpha B\). By Theorem 6.1, the tree height satisfies \(h \approx \frac{\log N}{\log B_{\text{eff}}} = \frac{\log N}{\log(\alpha B)} = \frac{\log N}{\log \alpha + \log B}\). Because \(\alpha < 1\), \(\log \alpha < 0\), which reduces the denominator and strictly increases the tree height \(h\), confirming inverse logarithmic dependence.

Tier 3 · Empirical

A market maker's tick database appends 50,000 quote updates per second. The primary table has 4 secondary indexes. If each secondary index insertion requires an average of 1.5 random page I/O writes, calculate the write I/O operations per second (IOPS) demanded of the storage subsystem.

Solution

Each quote update triggers 1 heap append write plus \(4 \times 1.5 = 6.0\) secondary index page writes, totaling \(1 + 6 = 7.0\) I/O write operations per row. At 50,000 updates/sec, the storage subsystem must sustain \(50{,}000 \times 7.0 = 350{,}000\) write IOPS. Without enterprise NVMe SSD arrays, the database will suffer severe write-stall queues.

In a database with 10 million rows, an index seek followed by a heap lookup takes 0.05 ms per row. A full table sequential scan takes a constant 200 ms. At what query selectivity (number of qualifying rows) does the sequential scan become faster than the index lookup?

Solution

Let \(k\) be the number of qualifying rows. Total time for index lookup is \(0.05 \times k\) ms. The sequential scan takes 200 ms. The break-even point occurs when \(0.05 k = 200 \implies k = 200 / 0.05 = 4{,}000\) rows. As a fraction of the 10 million row table, \(4{,}000 / 10{,}000{,}000 = 0.0004\) or 0.04% selectivity. For any query returning more than 4,000 rows, the sequential scan is faster.

A financial table uses random UUID strings as primary keys. After 5 million inserts, the index size is 800 MB with an average page fill factor of 52% due to random page splits. If sequential monotonically increasing integers had been used instead, the fill factor would be 95%. Calculate the storage space wasted by UUID fragmentation.

Solution

The raw key payload size is \(800 \text{ MB} \times 0.52 = 416\) MB. At 95% fill factor, the index would occupy \(416 \text{ MB} / 0.95 = 437.9\) MB. The wasted storage space is \(800 \text{ MB} - 437.9 \text{ MB} = 362.1\) MB (a 45.3% storage waste), which also pollutes the database buffer cache.

Tier 4 · Research

Analyze why Log-Structured Merge-trees (LSM-trees, used in RocksDB and DuckDB append logs) achieve higher write throughput than traditional B-trees for streaming financial ticks.

Solution

B-trees perform in-place updates on leaf pages, converting streaming writes into random I/O writes across disk blocks. In contrast, LSM-trees buffer incoming writes sequentially in an in-memory sorted buffer (MemTable). When full, the MemTable is flushed to disk as an immutable, sequential SSTable file using 100% sequential I/O with zero random writes. Background compaction threads merge sorted levels asynchronously. By trading background read amplification for pure sequential write bandwidth, LSM-trees achieve 10x higher write ingestion rates.

Evaluate the mechanics of bitmap indexing versus B-tree indexing for low-cardinality financial categorical attributes such as order side (BUY/SELL) or execution venue.

Solution

For low-cardinality attributes with few distinct values (e.g., BUY/SELL has cardinality 2), B-trees perform poorly because each branch has low selectivity. A bitmap index constructs a compact bit vector for each distinct value where bit \(i\) is 1 if row \(i\) has that value. Boolean query combinations (e.g. side = 'BUY' AND venue = 'NASDAQ') evaluate via ultra-fast hardware bitwise AND instructions on SIMD registers. However, bitmap indexes lock entire bit ranges on row modifications, making them ideal for read-only analytical warehouses but unusable for concurrent OLTP transaction engines.

Discuss how database index hints (e.g. FORCE INDEX) in production trading systems mitigate the risk of optimizer query plan flips caused by stale table statistics.

Solution

Relational query optimizers estimate plan costs using internal table histograms and cardinality statistics. In volatile trading sessions, sudden bursts of market orders or executions can shift table statistics, prompting the optimizer to suddenly flip execution plans from an index seek to a full table scan. In an algorithmic execution path, a plan flip causes query latency to spike from 100 microseconds to several seconds, risking massive trading loss. Forcing index hints guarantees deterministic access paths regardless of ephemeral table statistics.

7Retrieval quiz

  1. What is the search time complexity of a B-tree database index for key lookups?

    Options

    A B-tree provides logarithmic search depth \(O(\log_B N)\) by branching at each internal node.

  2. How many clustered indexes can a single database table possess?

    Options

    Because the clustered index dictates the physical sequence of rows on disk, a table can have only one clustered index.

  3. What is a covering index in relational databases?

    Options

    A covering index contains both the search predicates and projected attributes, satisfying the query directly from the index.

  4. In a binary search index over 10,000 sorted keys, what is the maximum number of comparisons needed to locate any key?

    \(\lceil \log_2(10{,}000) \rceil = 14\) comparisons.

  5. Why does using random UUIDs as primary keys degrade B-tree insertion performance?

    Options

    Random insertion destroys write locality, causing B-tree leaf pages to split frequently and halving page storage density.

  6. What trade-off is introduced by adding multiple secondary indexes to a high-frequency trading table?

    Options

    Every secondary index requires synchronous modification on every row insert, multiplying the write load.

  7. If a composite index exists on (symbol, date, time), can a query filtering strictly on 'date' use the index efficiently?

    Options

    B-trees are sorted lexicographically by the leftmost column; omitting 'symbol' forces an index scan or full table scan.

  8. Why does a query optimizer sometimes choose a full table scan over an available secondary index?

    Options

    When retrieving many rows, sequential disk scans outperform thousands of random I/O dereferences into the table heap.
