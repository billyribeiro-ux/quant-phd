Doctoral-level quantitative research requires unassailable reproducibility. If two researchers run the same backtest on what they believe is the same historical dataset and obtain different Sharpe ratios, the discrepancy is usually silent data divergence: an upstream vendor revised past rows, a download script truncated bytes, or file encoding corrupted special characters. A data manifest provides an immutable cryptographic audit trail. By recording exact origin URLs, licensing terms, UTC retrieval timestamps, row counts, and cryptographic SHA-256 digests over raw payload bytes, the data manifest guarantees bit-for-bit research verification and instant tamper detection.

1Data Manifest and Research Provenance

Building on point-in-time data, scientific quantitative workflows require explicit provenance tracking for every ingested dataset.

Definition 8.1 (Data Manifest)

A data manifest is an immutable ledger that records the provenance, licensing, retrieval metadata, and cryptographic fingerprint of every raw data payload ingested into a research platform. Each manifest record is a tuple: \[ M = (\text{source}, \text{sha256}, n_{\text{bytes}}, \text{rows}, \text{retrieved}, \text{licence}, \text{source\_url}), \] where:

  • Source (source): A validated identifier from an approved closed vocabulary (e.g. fred, french, shiller, treasury, edgar).
  • SHA-256 (sha256): The lowercase hexadecimal 256-bit cryptographic hash computed over the exact raw payload bytes.
  • Byte Count (\(n_{\text{bytes}}\)): Exact length of the payload in bytes (\(n_{\text{bytes}} \ge 0\)).
  • Row Count (rows): The number of data rows in structured tables (header excluded), or None for unstructured byte blobs.
  • Retrieval Timestamp (retrieved): The exact UTC timestamp in ISO 8601 format with trailing Z: YYYY-MM-DDTHH:MM:SSZ.
  • Licence (licence): Non-empty legal terms governing redistribution and usage.
  • Source URL (source_url): The authoritative network endpoint or file origin.

Remark 8.1 (Idempotence and Conflict Invariants)

A production data layer enforces two operational invariants:

  1. Idempotence: Re-ingesting the identical payload for the same source and retrieval timestamp returns the existing manifest record without writing duplicate observations or payload blobs.
  2. Conflict Detection: Ingesting a differing payload (different SHA-256 digest) under an already recorded (source, retrieved) pair raises a ValueError naming the conflict, preventing silent data mutation.

2Cryptographic Tamper Detection

The mathematical certainty of research data integrity rests on cryptographic hash properties.

Theorem 8.1 (Cryptographic Tamper Detection Invariant)

Let \(P \in \{0, 1\}^*\) be a raw data payload with cryptographic digest \(H = \operatorname{SHA-256}(P) \in \{0, 1\}^{256}\). If an adversary or hardware corruption mutates \(P\) to \(P' \ne P\) by flipping at least one bit (\(d_H(P, P') \ge 1\)), the probability that the mutated payload escapes detection under the verification check \(\operatorname{SHA-256}(P') = H\) satisfies: \[ \mathbb{P}(\operatorname{SHA-256}(P') = H \mid P' \ne P) \le 2^{-256} \approx 8.636 \times 10^{-78}, \] under the random oracle model. Thus, bit-level tamper detection succeeds with probability \(1 - 2^{-256}\).

Proof

The SHA-256 cryptographic hash function maps arbitrary-length bit strings to a 256-bit digest space \(\{0, 1\}^{256}\) of cardinality \(2^{256}\). By the design criteria of cryptographic hash functions (second-preimage resistance and the avalanche effect), changing even a single bit in the input produces an uncorrelated, pseudo-random output uniformly distributed over \(\{0, 1\}^{256}\). For any fixed \(H\), the number of preimages in the codomain that equal \(H\) is \(1\). Therefore, for any modified payload \(P' \ne P\), the probability that its pseudo-random hash value matches the pre-computed digest \(H\) is: \[ \mathbb{P}(\operatorname{SHA-256}(P') = H) = \frac{1}{2^{256}} = 2^{-256}. \] The probability of detecting corruption is \(1 - 2^{-256} > 1 - 10^{-77}\), which constitutes mathematical certainty for all practical computing environments.

Example 8.1 (Detection of a Single-Byte Corruption)

Suppose a Treasury yield snapshot contains 2020-01-02,1.88,1.55. If a disk error flips a single bit, turning 1.88 into 1.89, the SHA-256 digest changes completely: 

Original:  5ed16365311c1d28e6b3ddac7abc1cef41be7a959353fd63c70070ed910cab24
Corrupted: d4c52b233cc0fc0132d596724a942b3b469faf5f95cc0332e5d2e2ff049ce86e
A periodic verification pass immediately flags the mismatch and halts quantitative execution before corrupted yields reach portfolio optimizers.

Lab 1 · Data Manifest and Bit-for-Bit Cryptographic Integrity

Verifies that an immutable data manifest with SHA-256 hashes successfully validates clean payloads and triggers an immediate tamper detection failure when a single bit in the stored payload is flipped.

"""CS3 Lesson 8 Inline Lab 1: Data manifest and bit-for-bit cryptographic integrity.

Constructs an immutable data manifest with SHA-256 digests over raw payload bytes.
Verifies that flipping a single byte in a payload is detected with 100% certainty.
Data: SIMULATED market snapshots.
"""

from __future__ import annotations

import hashlib
from typing import NamedTuple


class ManifestRecord(NamedTuple):
    dataset_id: str
    source_url: str
    licence: str
    retrieved_utc: str
    n_bytes: int
    n_rows: int
    sha256: str


def compute_manifest_record(
    dataset_id: str,
    source_url: str,
    licence: str,
    retrieved_utc: str,
    payload: bytes,
    n_rows: int,
) -> ManifestRecord:
    digest = hashlib.sha256(payload).hexdigest()
    return ManifestRecord(
        dataset_id=dataset_id,
        source_url=source_url,
        licence=licence,
        retrieved_utc=retrieved_utc,
        n_bytes=len(payload),
        n_rows=n_rows,
        sha256=digest,
    )


def verify_integrity(record: ManifestRecord, current_payload: bytes) -> bool:
    """Verify that current_payload matches the cryptographic digest in record."""
    current_digest = hashlib.sha256(current_payload).hexdigest()
    return current_digest == record.sha256


def main() -> None:
    # SIMULATED CSV payload
    csv_text = "date,yield_10y,yield_3m\n2020-01-02,1.88,1.55\n2020-01-03,1.81,1.53\n2020-01-06,1.81,1.56\n"
    raw_payload = csv_text.encode("utf-8")
    record = compute_manifest_record(
        dataset_id="ust_daily_sample",
        source_url="https://atlas.local/data/ust_sample.csv",
        licence="SIMULATED: generated fixture",
        retrieved_utc="2020-01-07T18:00:00Z",
        payload=raw_payload,
        n_rows=3,
    )

    print(f"Dataset: {record.dataset_id}")
    print(f"Retrieved: {record.retrieved_utc}")
    print(f"Payload size: {record.n_bytes} bytes ({record.n_rows} data rows)")
    print(f"SHA-256 Digest: {record.sha256}")

    # 1. Verification of untouched payload
    clean_check = verify_integrity(record, raw_payload)
    print(f"Untouched payload integrity verified: {clean_check}")
    assert clean_check is True

    # 2. Tamper simulation: flip exactly one bit in payload
    tampered_bytes = bytearray(raw_payload)
    # Find position of '1.88' in payload and mutate character
    tampered_bytes[25] ^= 0x01  # Flip a single bit
    tampered_payload = bytes(tampered_bytes)

    tampered_digest = hashlib.sha256(tampered_payload).hexdigest()
    tampered_check = verify_integrity(record, tampered_payload)

    print(f"Tampered digest: {tampered_digest}")
    print(f"Tampered payload detected (check failed): {not tampered_check}")
    assert tampered_check is False
    print("Bit-for-bit tamper detection successfully triggered: True")

3Where the Canon Breaks

Data manifest systems must navigate subtle operational traps in quantitative research:

  • Character Encoding and Line Ending Drift: Ingesting a CSV file on Windows (CRLF \r\n) versus Linux (LF \n) alters byte content even if table values are identical. SHA-256 hashes the exact raw bytes, so line ending conversion fails hash checks. Ingestion pipelines must enforce byte-level UTF-8 normalization before computing digests.
  • Silent Upstream URL Rewrites: Web data sources frequently change their internal file URLs (e.g. moving from HTTP to HTTPS or shifting CDN domains). A manifest that records only the URL without payload bytes loses the ability to verify if the file content changed. The raw bytes must be stored alongside the manifest metadata.
  • Dynamic REST API Payloads: Querying a JSON REST API (such as company facts from SEC EDGAR) returns dictionaries with non-deterministic key ordering. Storing unparsed raw byte payloads guarantees bit-for-bit hash verification, whereas parsing and re-serializing risks key reordering differences.

4Misconceptions

  1. Recording the file name and download date is sufficient for data provenance.

    File names and download dates do not prove that file contents are identical. Vendors frequently overwrite files in-place with the same name. Only a cryptographic digest (SHA-256) over the exact bytes guarantees that historical datasets have not been altered.

  2. Hashing parsed table cells is better than hashing the raw byte payload.

    Parsing table cells introduces floating-point formatting ambiguity, whitespace trimming differences, and column ordering variations. Hashing the exact incoming byte stream ensures unassailable byte-level reproducibility before any data transformation occurs.

  3. Two different datasets could easily produce the same SHA-256 hash by coincidence.

    The probability of two distinct random payloads generating the same SHA-256 digest is approximately \(1\) in \(2^{128}\) (the birthday bound). This probability is smaller than the chance of a meteor striking a computer during query execution; accidental collisions are physically impossible.

5Problem Set

Tier 1 · Mechanics

A research assistant downloads an economic series file of length 1,048,576 bytes (1.0 MiB) on 2020-03-01T14:00:00Z. Write out the full manifest record tuple fields if the computed SHA-256 digest is a3f5... and the table has 12,000 data rows from FRED.

Solution

The manifest record fields are: source = "fred", sha256 = "a3f5...", n_bytes = 1048576, rows = 12000, retrieved = "2020-03-01T14:00:00Z", licence = "FRED terms of use", and source_url = "https://fred.stlouisfed.org/...".

What must a data layer store do if a user attempts to ingest an identical payload for source fred at the identical retrieval timestamp?

Solution

By the idempotence invariant, the store must recognize that the source, timestamp, and SHA-256 digest match an existing manifest row. It returns the existing ManifestRow without creating duplicate database rows or duplicate observation entries.

What must the store do if a user ingests a modified payload with a different SHA-256 hash under the same source and retrieval timestamp?

Solution

By the conflict detection invariant, attempting to store conflicting data under an already recorded retrieval timestamp raises a ValueError naming the conflict, preventing corruption of previously recorded research data.

Tier 2 · Proof

Prove that a SHA-256 hash digest is invariant under any database engine choice (e.g., SQLite vs DuckDB vs PostgreSQL) when computed over raw byte payloads.

Solution

SHA-256 is defined by FIPS PUB 180-4 as a deterministic mathematical function \(f: \{0, 1\}^* \to \{0, 1\}^{256}\) operating on binary bit sequences. Because the input to the hash function is the raw byte array of the payload prior to database storage or relational decoding, the input sequence is identical regardless of the downstream database engine. Because \(f\) is a pure mathematical function, identical bit sequences yield identical 256-bit digests across all operating systems and database architectures.

Prove that the birthday attack collision bound for SHA-256 requires generating approximately \(2^{128}\) distinct payloads to find two identical digests with 50% probability.

Solution

Let \(H = 2^{256}\) be the total number of possible hash outputs. By the classical birthday problem approximation, the probability \(P\) of at least one collision among \(k\) independently chosen random hashes is \(P(k) \approx 1 - \exp\left(-\frac{k^2}{2H}\right)\). Setting \(P = 0.5\) yields \(1 - \exp\left(-\frac{k^2}{2H}\right) = 0.5 \implies \exp\left(-\frac{k^2}{2H}\right) = 0.5 \implies \frac{k^2}{2H} = \ln 2\). Solving for \(k\): \(k = \sqrt{2 H \ln 2} = \sqrt{2 \ln 2} \times 2^{128} \approx 1.177 \times 2^{128}\) operations, which is physically infeasible with existing global computational power.

Prove that verifying a data manifest containing \(M\) datasets of total size \(S\) bytes requires \(O(S)\) sequential time and \(O(1)\) additional memory.

Solution

The verification algorithm iterates through each stored payload blob. For a payload of length \(L_i\), the SHA-256 streaming accumulator processes blocks of 64 bytes (512 bits) sequentially, reading each byte exactly once in \(O(L_i)\) operations while maintaining an internal state of eight 32-bit words (32 bytes). Comparing the resulting hex string with the manifest takes \(O(1)\) time. Summing across all \(M\) datasets: total time is \(\sum_{i=1}^M O(L_i) = O(\sum L_i) = O(S)\). Because payload chunks are processed in streaming buffers of fixed size (e.g. 64 KiB), additional memory overhead is strictly \(O(1)\).

Tier 3 · Empirical

A research firm audits 1,000 historical macroeconomic snapshots stored in SQLite. An automated tamper audit scans all payloads and computes SHA-256 hashes at 250 MB/s. If the total stored dataset size is 25 gigabytes, how many seconds does the full cryptographic audit take?

Solution

Total data size is \(25 \text{ GB} = 25{,}000 \text{ MB}\). At a throughput of 250 MB/s, total audit time is \(25{,}000 \text{ MB} / (250 \text{ MB/s}) = 100.0\) seconds (1 minute 40 seconds). The firm can audit the complete cryptographic integrity of its entire data foundation in under two minutes.

A market data provider updates an interest rate file. The initial file had 1,000 rows and SHA-256 digest 4a1b.... The new file has 1,005 rows and digest 9c8d.... If an analyst ingests the new file with the new retrieval timestamp, how many manifest rows exist in the store?

Solution

Because the new file has a different retrieval timestamp, it represents a new data vintage rather than a conflict. The store appends the new record as a new manifest row. The total number of manifest rows becomes \(1 + 1 = 2\) rows, preserving both historical vintages.

An analyst compares two copies of a 50 MB corporate fundamentals CSV. The first file uses Unix line endings (\n), while the second file was saved on Windows with CRLF (\r\n) across 500,000 lines. Calculate the difference in byte size and state whether their SHA-256 hashes match.

Solution

Each CRLF line contains 1 extra byte (\r). Across 500,000 lines, the Windows file is exactly \(500{,}000\) bytes (488.3 KiB) larger. Because SHA-256 hashes exact byte streams, the two digests will be completely different, failing byte-for-byte verification despite having identical cell text.

Tier 4 · Research

Analyze why data licensing and redistribution restrictions in quantitative finance necessitate "bring-your-own-data" research harnesses rather than bundling raw vendor datasets into shared repositories.

Solution

Commercial market data providers (Bloomberg, Refinitiv, S&P Capital IQ, CRSP) strictly forbid redistribution of raw tick or fundamental data under standard subscriber agreements. Violating terms of service exposes research institutions to copyright lawsuits and immediate terminal revocation. A "bring-your-own-data" harness provides deterministic parser adapters and manifest verification schemas: the repository ships only code and synthetic test fixtures, while researchers supply their own legally licensed data files locally, keeping data usage compliant.

Evaluate the security and performance implications of using Merkle Trees versus flat manifest lists for verifying large-scale partitioned tick archives in cloud object storage.

Solution

A flat manifest list requires rehashing all \(M\) file chunks to verify the archive, which is costly if an analyst wants to verify a single day's partition out of a 10-year archive. A Merkle Tree (hash tree) organizes chunk digests hierarchically: leaf nodes are chunk hashes, and parent nodes hash concatenated child digests up to a single Root Hash. To verify that a single 100 MB chunk is authentic within a 10 TB archive, the client needs only the chunk and a cryptographic audit path of \(O(\log M)\) sibling hashes, verifying integrity in milliseconds without downloading the entire dataset.

How does cryptographic data manifest verification integrate with Continuous Integration (CI) test harnesses to eliminate "silent data rot" in quantitative production pipelines?

Solution

In production trading desks, data rot occurs when upstream vendors silently modify historical data or network file systems suffer bit decay. A CI integrity job runs on a scheduled cron (e.g. nightly), re-reading every stored dataset and asserting that SHA-256(payload) == manifest.sha256. If any historical byte has shifted, the CI build fails immediately, blocking strategy deployment and alerting risk teams before corrupted inputs reach algorithmic execution models.
