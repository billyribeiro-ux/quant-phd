# E3 equivalent mutants

These files are student errors that the suite cannot separate from the reference on any input where the page states a
behaviour (ruling 9 in `plans/FINAL-ARCHITECT-RULINGS.md`). Each file is the current `course/modules/E/E3/grader/reference.py`
with one edit, regenerated by `ledgers/E3/scripts/fixer-d-r15/make_equivalents_r15.py`, and each section below gives the
difference and the proof. `tools/mutate_graders.py` never runs this directory.

# Tie-rule mutants (rulings 27 and 32)

The reference's `_half_up` is exact: it returns `math.floor(Fraction(y) + Fraction(1, 2))`, computed on the exact value of
the float `y`, so it is the nearest whole cent with an exact half going up. Each of the four files differs from the
reference only in its `_half_up` body:

| File | `_half_up` body in the file | Exact halves where the file differs from the reference |
|---|---|---|
| `f05_half_cent_goes_toward_minus_infinity.py` | `math.ceil(Fraction(y) - Fraction(1, 2))` | every half `k + 1/2` (the half goes down) |
| `m06_half_cent_rounded_to_even.py` | `round(Fraction(y))` | the halves `k + 1/2` with `k` even, such as 2.5 |
| `r13n01_half_cent_rounded_half_to_even.py` | `round(Fraction(y))` | the same set as m06 |
| `w05_half_cent_away_from_zero.py` | `floor(Fraction(y) + 1/2)` if `y >= 0`, else `ceil(Fraction(y) - 1/2)` | every negative half (none of the non-negative ones) |

**Difference set.** For a float `y` that is not an exact half, the nearest whole cent is unique, and all four files and the
reference return it, because they compute on the exact value. So the difference set is exactly the set of floats equal to
`k + 1/2` for an integer `k`, and the table above lists which of those each file changes. The measurement agrees
(`ledgers/E3/scripts/fixer-d-r15/tie_difference_probe.out`): over 228,000 candidate floats (every `k + 1/2` for
`|k| <= 2000`, the three floats on each side of each half, 200,000 random floats in `[-3000, 3000]`, and the two floats
nearest to 1/2 in absolute value), f05 differs on 4000 candidates, m06 and r13n01 on 2000 each, and w05 on 2000, and every
difference is an exact half. No candidate that is not an exact half differs.

**The float 0.49999999999999994.** This float is the largest one below 1/2. It is not an exact half, so it is outside the
difference set: the exact rule returns 0, and all four files return 0 too. The reference before this change computed
`math.floor(y + 0.5)`, which returns 1 at this float, because `y + 0.5` rounds up to 1.0 in binary64. That earlier
reference was therefore not the nearest whole cent at this float. The exact rule removes the error and changes the
reference's output at this one float from 1 to 0. No suite instance uses it: `instance.py` rejects a draw when a certainty
equivalent at the true parameters lies within `1e-6` of a half cent (`_clear_of_half_cent`, `_TIE_MARGIN`), and the
suite's only constructed tie is the one described in point 2.

## Why each one is equivalent to the specification

1. **Every output is a nearest whole cent.** The reference and each file return an integer at distance at most 1/2 from
   `y`, and they differ only when `y` is exactly `k + 1/2`, where both neighbours are at distance exactly 1/2.
2. **The page accepts either neighbour at an exact half cent in the two places where `_half_up` is used.** (a) Under the
   prospect model the value is a float, so an exact half cent may come out on either side, and the prospect check accepts
   either whole cent within half a cent of the exact sure amount. (b) Under the CRRA model with `gamma != 0` the value is a
   float too, so an exact tie may come out on either neighbouring cent (ruling 27). The suite's CRRA tie test
   (`test_crra_exact_tie_at_nonzero_gamma_accepts_either_neighbour`, gamma = 1/2, exact value 219.5 cents) accepts 219 or
   220, and the CRRA risky-lottery check allows half a cent of slack. Both sentences are in the Whole cents paragraph of
   `course/modules/E/E3/project.html`.
3. **The CRRA exact path at `gamma = 0` does not call `_half_up`.** It rounds an exact `Fraction` with
   `floor(expected + 1/2)`, so none of these files changes that output.
4. **No suite instance lands on a tie.** `instance.py` rejects a draw when a certainty equivalent at the true parameters
   lies within `1e-6` of a half cent, so the suite's own participants cannot separate the files.
5. **Evidence.** Each file passes the whole suite on seeds 0 to 9 (see the seed runs listed under "Evidence of this round"
   below).

# Gamma-clamp mutants (rulings 28 and 32)

Ruling 32 narrows the estimator's stated range to `gamma_hat` in `[0.001, 0.99]` (the Estimation convention of
`project.html`). Each clamp changes the reported `gamma_hat` only outside that range, so each file stays here:

| File | Change in `estimate` | Differs from the reference only when | Position relative to the stated range |
|---|---|---|---|
| `r11_03_gamma_hat_clamped_below_one_minus_1e3.py` | `min(..., 0.999)` | `gamma_hat > 0.999` | outside (above 0.99) |
| `r12d_03_reported_gamma_floored_at_one_thousandth.py` | `max(..., 0.001)` | `gamma_hat < 0.001` | outside (below 0.001) |
| `v15d_03_reported_gamma_clamped_at_0_99.py` | `min(..., 0.99)` | `gamma_hat > 0.99` | outside (above 0.99) |

**Measured, not assumed.**

- **Inside the range the reference passes the local-maximum check.** `ledgers/E3/scripts/fixer-d-r15/inrange_localmax_probe.py`
  (outputs `inrange_high.out` and `inrange_low.out`) fitted 84 converged participants with `gamma_hat` in `[0.9, 0.99]`
  (largest 0.987361) and 31 with `gamma_hat` in `[0.001, 0.1]` (smallest 0.001368). All 115 pass the page's check: no 0.1
  percent move raises the log-likelihood by more than 1e-9.
- **Above 0.99 the reference does converge, and the check can fail there.** The targeted probe
  (`ledgers/E3/scripts/E3-d-r15/gamma_high_probe_r15.txt`, 480 low-noise participants) had 294 converged fits, the largest
  `gamma_hat` 0.994442. `ledgers/E3/scripts/fixer-d-r15/fit_0994_localmax.out` measures that fit (gamma truth 0.99,
  lambda 1, kappa 20, 26 answers, simulation seed 2): a 0.1 percent move in gamma raises the log-likelihood by 2.735e-9,
  above the 1e-9 bound. This is why the range stops at 0.99. No converged fit above 0.999 was found in 4000 random trials
  (`ledgers/E3/scripts/E3-d-r15/gamma_scan_high_4000_r15.txt`, `HIGH hits 0`).
- **Below 0.001 the reference does converge.** The 2000-trial scan (`ledgers/E3/scripts/E3-d-r15/gamma_scan_low_2000_r15.txt`)
  found 85 converged fits with `gamma_hat < 0.001`, from 7.2e-13 up to 8.6e-4. These lie outside the stated range.
- **The suite's own participants stay inside the range.** Over the 792 estimates of seeds 0 to 399 (each own participant and
  each second participant), the largest `gamma_hat` is 0.98639 (own seed 352) and the smallest is 0.02489 (own seed 373).
  The eight raising participants return no estimate.

So a clamp at 0.999, 0.99 or 0.001 changes an output only where the page states no outcome, and the three files are
equivalent under ruling 32. `v15d_03` was written in round 15 and moved here from `mutants/` for that reason.

# Removed: e12_03 (ruling 28)

`e12_03_search_returns_silently_when_it_stalls.py` is deleted. Its only difference from the reference was that it
returned the stalled point where the reference raised `the step became negligible before the score did`, the branch of
`_maximise` entered when the step becomes negligible before the score does and polishing does not move the point. No
run in the round-14 evidence reached that branch: the eight raising runs raise the other two messages, and every returning
run ends before it. Ruling 28 treats the branch as dead code, so the reference no longer raises there. It now ends the
search with `break`, and the error after the loop (`the likelihood maximisation did not converge`) reports the stall.
The mutant is removed with it. Git shows the file as renamed to `ledgers/E3/mutants/r14d_02_crra_log_case_takes_logs_of_final_wealth_minus_wealth.py`
with changed content; that file is a different student error (the CRRA log case), so the deletion stands. The round-15 probe (`ledgers/E3/scripts/E3-d-r15/verifier/stall_branch_probe.out`) reports
`STALL_BRANCH_HITS 0` over the 800 participants of seeds 0 to 399.
